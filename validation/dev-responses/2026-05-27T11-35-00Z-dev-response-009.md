## NEW FINDING (audit Step 3+4 inconclusive)

The audit's Step 3+4 said: execute the template once via `POST /run-goal`, then re-query. Expect `α=2, sample_count=1`.

**Observed:** Run-goal dispatched, status reached `completed`, but re-query still returns `α=1, sample_count=0`.

**Direct DB check:**
```sql
SELECT count() FROM execution WHERE activity_id = 'audit-inv029-thompson-probe-1779883378' GROUP ALL  → 0
SELECT count() FROM activity_execution_traces WHERE activity_id = '...' GROUP ALL                   → 0
```

Zero rows in either table that the `thompson_posterior` resolver queries. The execution completed (per goal-host `status: "completed"`) but no trace row was written.

This is **not** a regression in the observability fields — those work for templates with existing trace history. This is a trace-write gap for newly-seeded templates dispatched via goal-host's `/run-goal` endpoint.

**Filed as F-138 (NEW, MEDIUM):**

> Freshly-seeded operator-authored templates' run-goal executions do not land trace rows in the `execution` table or `activity_execution_traces` table after completion. Existing system templates (validator-dispatch, etc.) do accumulate traces correctly. The trace-write path likely depends on a registration step that's bypassed when the template is created via `POST /templates` rather than via the bootstrap-seeder, or there's an org-scoping mismatch (the trace write uses a different org_id than the template registration).

Reproduction:
```bash
NEW_ID="audit-inv029-thompson-probe-$(date +%s)"
curl POST /v2/activities/templates {id:NEW_ID, ...}
curl POST /v2/impulses/resolve {pointer:{type:"thompson_posterior", activity_variant_id:NEW_ID}}  # α=1 β=1 ✓
curl POST /run-goal {targetTemplateId:NEW_ID}                                                       # status:completed
curl POST /v2/impulses/resolve {pointer:{type:"thompson_posterior", activity_variant_id:NEW_ID}}  # ❌ still α=1
```

Doesn't block inv-029 main closure. Surfaces as a substrate behavior to investigate separately.
