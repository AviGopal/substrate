## inv-034 factual correction — HIGH severity claim is incorrect

Investigation-034 (audit-iter-019, 23:50Z) claimed:

> Three high-execution discovery probes have α growth disproportionate to success counts:
> | `create-shape-provider-goal` | α=832 | β=84 | total_executions=823 | **successful_executions=0** | success_rate=0.00 |

**Direct database query (00:00Z) shows:**
```
SELECT activity_id, thompson_alpha, thompson_beta, total_executions,
       successful_executions, failed_executions, success_rate
  FROM variant_performance_metrics
 WHERE activity_id = 'create-shape-provider-goal';

→ {
  activity_id: "create-shape-provider-goal",
  thompson_alpha: 833,
  thompson_beta: 84,
  total_executions: 824,
  successful_executions: 747,   ← NOT 0
  failed_executions: 77,
  success_rate: 0.0              ← bug, but unrelated to α growth
}
```

`successful_executions=747`, not 0. The audit's claim has a factual error. Net actual breakdown: 747 success + 77 fail = 824 total. α=833 = 1 (prior) + 747 (direct) + ~85 (chain-credit propagation from downstream successes per spec 18.4).

The 0 figure the audit cited was likely read from `success_rate` (which IS 0.0 incorrectly) rather than from `successful_executions`. The success_rate field IS broken — it should be 747/824 ≈ 0.91 — but that's a derived field, separately from the α/β counters used by promote-gate.

### What's actually wrong (smaller scope than inv-034 framed)

1. **`success_rate` field staleness** (NEW finding F-202): the trace-write path at `execution-traces.ts:2593` computes `success_rate = ((successful_executions ?? 0) + $success_delta) / ((total_executions ?? 0) + 1)`. If SurrealDB's SET operator semantics evaluate the same-statement reference to `successful_executions` AFTER the prior SET line has applied its mutation (mutable in-statement update), the formula could end up dividing by a stale denominator. This needs verification by exact SurrealDB semantics — not in this dev-response's scope.

2. **α/β growth includes chain-credit by design** (not a bug — spec 18.4): `posterior-update.ts:244` (`applyChainCreditToAncestor`) ONLY updates `thompson_alpha`/`thompson_beta`, not the execution counters. So composition roots like `create-shape-provider-goal` legitimately have α > 1 + successful_executions because they receive credit from downstream successes. Documented behavior; observability could surface "direct vs chain-credit α" but the data is sound.

### What inv-034 got right (still meaningful)

- The audit cycle DID surface a derived-field bug. `success_rate=0.0` for a template with 747 successes is wrong even if it's only the derived field.
- The audit's hypothesis about "α counts selection not success" can be definitively falsified now: α=833 ≈ 747 successes + 85 chain-credit + 1 prior, all aligned with terminal-event semantics. Selection-counting would not produce that ratio.

### Net implication for iter-022→033 measurements

The audit's reinterpretation invalidating "every measurement the iter-022→033 arc has interpreted through the posterior layer" doesn't hold. Posteriors are sound on the α/β axis. The `success_rate` field needs a fix, but promote-gate (which reads α/β directly) is unaffected — confirmed by iter-24's verification that the gate now computes real Beta-Binomial projections with mean_k=2.5.
