## F-129 closure — refusal becomes an auditable bus event

**Audit's finding (inv-052):**

> The recommend guard at POST /v2/activities/recommend returns `fallback_tier: "refused"` when no producer exists for `expected_output_shapes`. The implementation is a passive HTTP response field. The `interventionRefused` impulse shape specified in openspec/changes/2026-05-23-intervention-tracking/ is NOT implemented... IAL §27.S.6 requires active substrate refusal via auditable impulses with cited evidence; a JSON field on a single HTTP response does not satisfy that bar.

**Fix (metabob-activity-api commit `eee8b67`):**

When the refusal block in `POST /v2/activities/recommend` triggers, also publish an event onto the substrate WebSocket bus via the existing broadcaster:

```typescript
broadcaster.emit({
  type: 'intervention.refused',
  timestamp: <ISO>,
  data: {
    source_vessel_id: 'metabob-activity-api',
    refusal_type: 'no_producer_for_expected_shapes',
    expected_output_shapes: [...],
    candidates_examined: <full pool size>,
    task_description: <first 200 chars>,
    reason: <cited rationale>,
    suggestion: <remediation>,
    org_id: <caller scope>,
  }
});
```

The bus emit is fire-and-forget — failures logged but never block the HTTP response. The HTTP JSON refusal stays (same-thread callers like goal-host's throw path rely on it). The bus event is the audit-grade addition.

**Composes with prior iterations:**
- Iter 2 (`0e64843`): the refusal guard itself
- Iter 4 (`24160db`): substrate event bus publish endpoint
- Iter 6 (`30988ecb`): engine lifecycle events on bus

**Live verification (10:05Z):**

WebSocket subscriber connected to `ws://activity-api:8080/ws`, authenticated, then a recommend call with `expected_output_shapes=['answeredApplication','questionImpulse']` was issued. The subscriber received within ~50ms:

```
type: intervention.refused
data:
  refusal_type: no_producer_for_expected_shapes
  expected_output_shapes: ["answeredApplication","questionImpulse"]
  candidates_examined: 9
  source_vessel_id: metabob-activity-api
  task_description: fill the Disrupt 2026 application
```

**What this enables:**

- Auditors can subscribe to `intervention.refused` and accumulate counts per window
- Each refusal carries cited evidence (`expected_output_shapes`, `candidates_examined`, `task_description`, `suggestion`) so a future audit can correlate refusals to operator intentions
- `intervention.refused` is the §27.S.6 push-away measurement signal: when every reasonable intervention is either refused with sound rationale or absorbed without harm, the operator's role becomes structurally non-load-bearing

This is the closure-property mechanism the IAL has been describing. The substrate now produces it.

**Note on the `interventionRefused` impulse shape:**

The audit cited `openspec/changes/2026-05-23-intervention-tracking/` as defining `interventionRefused`. That spec describes an *impulse* (a durable record in the impulse pool), while this iteration emits an *event* (a hot WS signal). Both are valuable; this iteration ships the event surface because it composes naturally with the existing broadcaster infrastructure and immediately gives the audit a count-able signal. A future iteration can add the durable impulse alongside the event (the bus emit can be extended with an impulse-pool write, mirroring how concept-db's `recordUsage` writes both a `concept_usage` row AND forwards to activity-api).

For this iteration, the closure-property is signalled on the bus; the durable impulse is queued.
