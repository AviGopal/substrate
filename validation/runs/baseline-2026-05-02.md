## The single divergence point

minibob fails the same way every time: exit 1, exactly 4 LLM calls, 0 tool calls, ~17.1k input tokens, ~116-121 output tokens. The numbers are uniform across all 4 prompts and both workspaces — it's the **same canned failure path**, prompt-independent.

Reading `transcript.jsonl` from 01-fix-failing-test × typescript:

> `<impulse_context>...</impulse_context>` ... `Input envelope (JSON): {"error":true,"shape":"discoverByShapesQuery","message":"impulse-resolve(discoverByShapesQuery) failed: MCP impulse resolution failed: Failed to resolve impulse: 503 Service Unavailable","degraded":true}`
>
> ... LLM correctly returns `{"selected":null,"unbindable":true,"reason":"no validator candidates returned by discoverByShapesQuery"}`
>
> ... `lifecycle:task:completed` event fires, no further LLM calls, exit 1.

**Root cause.** minibob's `goal_processing_activity_driven` template calls `discoverByShapesQuery` for variant selection. In `--no-backend` mode that resolution returns a degraded `503 Service Unavailable` impulse. The selection-LLM correctly emits `unbindable: true`. The meta-activity dispatcher treats unbindable as fatal and aborts the goal — **never falling back to the improviser**.

**The improviser path exists** (`src/improviser.ts`, ~1709 LOC, has the free-form tool-use loop with retry-on-feedback). It is unreachable in `--no-backend` mode because the goal-processor's activity-driven path commits to discoverByShapesQuery before any standalone-mode bypass.
