## ISS signature is NOT in the engine

Critical finding: `state_space_signature` is computed **entirely at the activity-api edge** (`execution-traces.ts:2375-2398`, `session-context.ts:141-164`). The engine and the LLM resolver are signature-blind. The signature is read from `body.metadata.state_space_signature` if the client (minibob today, ias-executor when wired) attached it; otherwise the route re-derives from `body.input_impulse_shapes + metadata.provenance + metadata.missing_shapes`. Consumed by `applyOutcomeToPosteriors → posterior-update.ts:476-533`, which writes a stratified row into `context_thompson_scores` keyed on `(org_id, template_id, signature_version, context_bucket=signature)`.

So today: signature is a property of the **outcome write** and **recommendation read**, computed at the activity-api edge. It is not in `ResolverContext` and not carried on any lifecycle event.

## The conditional-posterior corruption surface, with bleed paths

Two posterior stores:
- `context_thompson_scores` — keyed on `(template_id, signature_version, signature)`. Signature-bucketed.
- `variant_performance_metrics` — unconditional. NOT signature-keyed.

**Conditional bucketing isolates corruption.** Pre-iter-026 confabulation under signature S1 pollutes row `(T, 1, S1)` only. The same template under S2 gets its own row, untouched. iter-026 makes future S1-incoming requests still see the same biased S1 α — bucketing **isolates** but does **not heal** the corruption.

**Unconditional metrics are the bleed path.** Recommendation tiers that fall back to the unconditional posterior (cold-start signatures with no matching `context_thompson_scores` row, or templates below the `CARDINALITY_CAP=200` threshold) read the polluted average. Cold-start traces (high confabulation rate) typically outnumber mature traces (low confabulation), so the unconditional row skews toward the corrupted regime.

**Chain-credit is a cross-signature leak.** `posterior-update.ts:236-302` propagates α/β to ancestors using each ancestor's own signature (`ancestor_signatures` map). After iter-026, if `synthesisOutcome=insufficient_signal` flips a trace from `success=true` to `verifier_negative`, chain-credit walks ancestor signatures and writes negative deltas to each. Ancestors whose signatures did not include `synthesisOutcome` at the time they ran will receive negative delta on rows that predate the new shape — retroactively pushing β onto historical buckets keyed on signatures that never knew about the new shape. **Correct in intent** (the ancestor really did fail because of a downstream gap) but means Phase 24 cannot fully sandbox pre-/post-iter-026 evidence per signature.

**Operator action implied:** post-iter-026, **decay or reset `variant_performance_metrics` for templates with `unmetRequirements`-producing variants more aggressively than `context_thompson_scores`** — the former is contaminated by averaging, the latter only contaminated where it was already mis-signaling.

## Validator-dispatch with the new shapes — zero lifecycle changes needed

Two coherent routes for `synthesisOutcome=insufficient_signal`:
1. **Run validators against the `synthesisOutcome` impulse itself** — validator checks the LLM's self-report matches the actual input-impulse evidence. Catches the **inverse** of iter-024's confabulation: LLM falsely declares insufficient when inputs were adequate.

## The single highest-leverage lifecycle event to add: `lifecycle:llm:dispatched`

**Why this over all the others:** iter-026's correctness *cannot be verified* without it.

Once `llm-prompt.ts` is patched to read `context.inputImpulses`, the operator-facing question is: *"did the model actually see them, or did the merge silently drop them, or did the model see them and still confabulate?"* Today there is no event that captures the rendered prompt — the resolver returns text, the engine stores impulses, and the trace stores `inputImpulseIds` but not the prompt-as-rendered.

**Without `lifecycle:llm:dispatched`, both the iter-024 confabulation audit and the iter-026 attribution-fix verification reduce to log archaeology.**

With it:
- Validator-dispatch can subscribe and assert "rendered prompt contains the input-impulse content" as a deterministic check.
- Phase 24 signature-conditioned posteriors gain a verifiable confabulation-rate metric per signature bucket — closing the corruption-surface analysis with measurement rather than inference.
- iter-024's `(signal-empty AND confident-output AND downstream-fail) / (signal-empty AND any-output)` ratio becomes computable from event stream, not log scraping.

**Emit site:** `llm-prompt.ts` after interpolation, before `llm.generate`. **Payload:** `{executionId, taskId, templateId, renderedPrompt, inputImpulseIds, inputShapes, variables}`. **Subscribers:** confabulation audit harness; eventually Cβ concept-extractor for prompt-→-outcome co-occurrence learning.

The other proposed events are observability niceties. This one is the audit primitive without which the iter-026 correction cannot be proven to work.

## LLM resolver should be a lifecycle PRODUCER, never a SUBSCRIBER

- **Long-running LLM observing sibling-task completion:** misuse. Inverts stateless-resolver contract. The right place is a meta-activity subscribed to `lifecycle:task:completed`.
- **LLM reacting to `lifecycle:substrate:idle` for pre-computation:** misuse. Token costs uneconomic; boredom-vessel + meta-activity already covers this.
- **LLM resolver emitting `lifecycle:llm:dispatched`/`lifecycle:llm:returned` for audit:** correct use. Resolver is the only place that knows the rendered prompt and raw model response.

**The asymmetry matters:** the LLM resolver should be a producer on the lifecycle channel but never a subscriber. Subscription implies long-lived state breaking the stateless-resolver invariant.
