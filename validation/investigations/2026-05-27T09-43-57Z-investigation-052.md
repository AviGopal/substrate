The development-vessel submodule advanced to `c412e5d`. The change is in `repos/development-vessel/src/resolvers/reachable-unlearned-report.ts`.

**What the code does:**

1. Fetches a 24-hour-wide trace window in addition to the 1-hour lookback window.

## Commit 5: 4ec72006 — reactive proxy registration

**What landed:** goal-host-vessel gets a WebSocket subscriber (`startVesselRegistrationSubscriber()`) that:
1. Connects to `${ACTIVITY_API_ENDPOINT}/ws`
2. Authenticates with ApiKey
3. Filters for `{type: "vessel.registered", data.vessel_id === DEV_VESSEL_ID}` messages
4. Debounces 500ms, then calls `registerDevVesselProxies()`
5. Reconnects with exponential backoff on close/error

Also: `BusForwardingEventSink` from `@avigopal/ias-executor-ts/adapters` is wired in goal-host-vessel — engine lifecycle events now forward to the bus.

**Live verification from logs:**

The 09:18Z restart shows startup-path proxy registration (30 shapes, fast). The 09:20Z restart shows reactive-path proxy registration:
```
09:20:38Z — goal-host started
09:20:38Z — "vessel-registration subscriber started → ws://127.0.0.1:8080/ws"
09:20:43Z — "proxy registration: +30 new shapes (now 30 total)"
```

The 5-second gap is the WS connection + authenticate handshake + dev-vessel heartbeat triggering the subscriber. The startup-path `/shapes` fetch likely succeeded in this case (dev-vessel was already up); but the reactive subscriber also fires, causing the `+30` re-registration. The `Set`-based diff logic de-duplicates, so no corrupted resolver state.

**F-129 original scenario dissolved:** The race — goal-host starts before dev-vessel, one-shot fetch gets zero shapes — is now healed by the reactive subscriber. When dev-vessel eventually registers, discovery-vessel emits `vessel.registered`, goal-host's subscriber receives it and calls `registerDevVesselProxies()`. Operator intervention no longer required.
