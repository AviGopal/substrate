## The F-022 clock-view pattern

For the second iteration (iter-005 first, this one second), the
auditor's `date -u` returned a stale value on the first
invocation and a fresh value on a later invocation, with the
delta growing over the iteration's wall-clock run.

This iter:
- First `date -u`: 06:11:14Z
- Later `date -u`: 07:00:44Z (delta: 49 minutes)
- Substrate's `date -u` (from inside container): 07:00:44Z
- Boredom timer log timestamps (06:20, 06:30, 06:40, 06:50): consistent with the substrate's clock

The substrate clock is the authoritative reference. The agent's
first `date -u` was 49 minutes stale; subsequent commands took
real wall-clock time and the substrate clock advanced
accordingly.

Implication for the audit's provenance discipline: `date -u`
must be called near the report-write step, not at iteration
start. This iter uses 07:00:44Z (the substrate-consistent
value).

The pattern is consistent across iter-005 and iter-010. Likely
cause: the agent's bash tool returns cached output for the
first call in a fresh session, then catches up on subsequent
calls. Worth understanding but not blocking.
