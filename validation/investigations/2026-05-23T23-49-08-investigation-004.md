## New findings

### F-020 (medium) — Narrator WebSocket event capture inactive

The narrator is running and producing snapshots, but no
`events-<date>.jsonl` file exists in `validation/observations/`.
The substrate-narrator.ts script's WebSocket subscription to
activity-api `/ws` appears silently inactive. Five snapshots
produced over ~16 minutes; zero events captured.

The substrate's task lifecycle (task.started, task.completed,
task.failed, tool.call, impulse.resolved) IS active — F-017 in
iter-003 confirmed live traces are landing. So the WebSocket
endpoint is producing events; the narrator just isn't capturing
them. Likely cause: the WS auth path uses a different credential
or endpoint than the HTTP snapshot path. F-019 (discovery-vessel
401) suggests a broader cross-vessel auth divergence; WS may be
hitting the same auth quirk.

Without event capture, our audit can only sample momentary state.
We can't observe the substrate's behavior over a window — which
is precisely what the narration protocol exists to enable.

### F-021 (medium) — Concept-db missing from snapshots

`docs/SUBSTRATE_NARRATION_PROTOCOL.md §B.1` names concept-db as
the first item on the substrate's t-0 knowledge surface. The
narrator's snapshot captures it as `{ endpoint: null, reachable:
false, error: "not configured" }`. The substrate has a concept-db
vessel (per `repos/concept-db/`) but the narrator has no URL for
it.

This means our snapshots are systematically incomplete. Auditing
substrate self-knowledge requires the substrate's full t-0
surface; missing one component means findings about substrate
knowledge gaps could conflate "missing from this snapshot" with
"missing from the substrate."

Operator remediation: add `CONCEPT_DB_URL` to the narrator's
environment or to `~/.metabob/config.json` under
`conceptDb.endpoint`.
