## Part 3 — Is S.4a actually blocked, and why?

The validator's instinct is correct even if the framing is wrong. S.4a IS blocked — but structurally, not by timing.

**What coverage_progress requires:** The `resolveCoverageTick` resolver (development-vessel `src/resolvers/coverage-tick.ts:168-174`) computes `coverage_progress = true` when:

1. `reachable_learned` is **strictly increasing** across all 4 consecutive 1h windows (1h, 2h, 3h, 4h lookbacks)
2. `reachable_unlearned` and `unknown` are non-increasing
3. `consecutive_progressing_cycles >= 3`

**Simulation against current full trace corpus (841 traces, 23 advertised shapes):**

```
-1h window:  traces=346  RL=13  RU=10
-2h window:  traces=701  RL=17  RU=6   (+4 PROGRESSING)
-3h window:  traces=834  RL=17  RU=6   ( 0 STAGNANT)
-4h window:  traces=841  RU=17  RU=6   ( 0 STAGNANT)

progressing_pairs = 1 of 3 required
coverage_progress = FALSE
```

The 1h → 2h window shows improvement (+4 RL, from 13 to 17). But 2h → 3h and 3h → 4h are flat. This means **the substrate learned 4 new shapes between 2h ago and 1h ago, but hasn't learned any new shapes between 3h ago and 2h ago** — because the same templates have been executing throughout.

**The structural cause (F-075):** Thompson Sampling has driven the boredom rotation to overwhelming validator-dispatch dominance. Of 841 traces, validator-dispatch accounts for ~470 (56%) and slot-binding ~83 (10%). These two templates together produce shapes that are already learned (`activityRecommendation`, `activity_template`, `recommendation`, `activityTemplateVariant`). The 6 unlearned shapes (`commandResult`, `fileEditResult`, `judgmentPropagated`, `sensitivity_evidence`, `test_audit_report`, `vesselScaffolded`) are advertised by templates that are either failing (create-shape-provider-goal) or not being selected by Thompson.

**Will the next coverage-tick run (expected ~11:29Z) show coverage_progress=true?** Only if new shape-producing templates execute in the next 60 minutes that haven't been executing in the 2h window. With Thompson at α=251 for validator-dispatch and the current rotation, this is unlikely without operator intervention.

**Conclusion:** The validator's "irreversibly blocked" label is wrong on timing but right on substance. The block is structural: RL saturates beyond 1h because the same templates keep running. Fixing it requires either (a) seeding new templates that produce unlearned shapes or (b) operator force-selection of templates producing `commandResult`, `fileEditResult`, etc.
