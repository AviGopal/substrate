## §2 — Concept-db idempotency surface (verified)

`repos/concept-db/src/resolvers/concept.ts:692-768` exports `upsertBySignature(pointerType, shape)` which:

- `SELECT * FROM concept WHERE source_type='impulse_signature' AND pointer.type=$pointerType AND shape=$shape LIMIT 1`
- Returns existing if found (`created: false`), else `CREATE` with id `signature:<pointerType>:<shape>` (the comment block at `:700` confirms canonical id form).

This is the **only first-class upsert path** — and it's hardcoded to `source_type='impulse_signature'`. For a doc-ingest pipeline we either (a) reuse this path by overloading `source_type='impulse_signature'` (semantic abuse — that source_type is reserved per the schema's enum at `001-concept-tables.surql:28-39`, which does NOT include `vessel_construction_pattern` in its hard ASSERT — the enum is `goal | memo | human_input | search | llm | metabob_annotation | write | read | cpg_embedding | extracted`; verified) or (b) compute a stable concept id externally and use `CREATE OR UPDATE` semantics not currently exposed.

**Wait** — `seed-claudemd.ts` posts `source_type: "vessel_construction_pattern"` which is **NOT in the ASSERT enum**. Either the enum has been relaxed (since aebdd21e shipped) or the script silently fails for non-enum source_types. Quick check: `repos/metabob-mcp/src/tools/concept-create.ts:46-52` lists `SOURCE_TYPES` including `'vessel_construction_pattern'` and `'impulse_activity_pattern'`. So either the schema enum was widened post-001-concept-tables.surql, or the MCP tool's POST bypasses the table-level ASSERT (concept-db likely sets these via the resolver layer which may use root privileges). This is a **separate finding** but not load-bearing for this design — operationally the writes work.

**Decision**: for broader ingest, the pipeline must compute a deterministic concept id `<source_family>:<file_path_hash>:<section_hash>` and use `PUT /concepts/{id}` semantics — which concept-db does NOT currently expose for arbitrary source_types. Therefore the ingest pipeline either (i) adds a new endpoint (small concept-db patch) OR (ii) does a SELECT-then-POST-or-PATCH check-first dance over HTTP.

## §7 — Idempotency strategy

Stable concept id formula: `ingest:<family>:<sha256(path)[0:8]>:<sha256(section_title)[0:8]>`. Examples:

- `ingest:openspec_change:a3f7e9b1:c2d4e6f0` for `openspec/changes/2026-05-23-substrate-explicit-vessels/design.md#substrate-vessel-bootstrap`
- `ingest:script:91b2c3d4:00000000` for `scripts/concept-seed/seed-claudemd.ts` (no section)

Re-ingest semantics:
- **Body changed**: UPDATE existing concept's `content`, `summary`, `updated_at` (concept-db's `updated_at VALUE time::now()` at `001-concept-tables.surql:69` auto-stamps).
- **Section/file removed**: leave concept; set `priority = priority * 0.5` (decay-to-stale). Per iter-066 substrate-doesn't-deprecate discipline; downstream relevance scoring handles fade-out.
- **Edges removed when section reorganized**: leave edges intact. Per the substrate principle of additive-only learning, stale edges decay via `times_traversed` not increasing.

**Required concept-db change** (small): expose `PUT /concepts/{id}` (or `POST /concepts` with `id_override` param) so ingest scripts can compute id externally and avoid the SELECT-then-POST dance. Without this, every ingest run is O(N) SELECT calls. ~30 LOC in `concept-db/src/routes/concepts.ts`.
