## Spec: `2026-05-27-neutral-emitter-lifecycle-bus`

**Five files written:**
- `proposal.md` — Why + What Changes + Capabilities + Impact + Dependencies
- `design.md` — architectural decisions, publish-via-HTTP rationale, taxonomy, trade-offs, risks, out-of-scope
- `tasks.md` — six task groups with concrete subtasks
- `specs/lifecycle-events-bridge/spec.md` — ias-executor-ts → bus contract
- `specs/vessel-registration-events/spec.md` — discovery-vessel → bus contract
- `specs/proxy-resolver-reactive-registration/spec.md` — goal-host subscriber contract

**Key design decision:** the bus is not new. Activity-api's existing WS broadcaster (`repos/metabob-activity-api/src/websocket/broadcaster.ts`) is the canonical fan-out. The defect is not "missing bus" but "trapped events that never reach the bus." Three classes are bridged:

1. `ias-executor-ts` engine lifecycle events (`lifecycle:task:preBinding`, `lifecycle:execution:succeeded`, etc.)
2. `discovery-vessel` registration mutations (register / heartbeat / expire)
3. (Out-of-scope here, follow-up) `concept-db` internal events

**Publish/subscribe asymmetry:** vessels publish via `POST /v2/events/publish` (fire-and-forget HTTP); subscribers consume via the existing `wss://activity-api/ws` connection. Mirrors how trace storage works (POST to write, WS for reactivity). Keeps reconnection state in subscribers.

**Event taxonomy:** dotted snake_case, 2-4 segments. Validated at the publish boundary.

## Phase 1 implementation (DONE — task 1)

**Commit:** `24160db` (metabob-activity-api)

`POST /v2/events/publish` accepts `{type, source_vessel_id, scope?, target?, data}`. Type matches `^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*){1,3}$`. Default scope=broadcast; `scope=org` and `scope=session` route to `emitToOrg` / `emitToSession`. Broadcaster failures logged but never propagate (best-effort bus).

**Tests:** 8/8 unit pass. Live verified: bogus type → 400 with reason; valid type → 200 + WS fan-out.

**Activity-api `WebSocketMessage.type` widened** to accept open-ended event-type strings alongside the existing typed union. Existing event types unchanged.

## Phase 4 implementation (DONE — task 4)

**Commit:** `64489e2` (discovery-vessel)

Discovery-vessel emits three vessel events:
- `vessel.registered` — after `register()` succeeds; includes `vessel_id`, `shapes`, `resolve_endpoint`, `resolve_request_format`, `auth_scheme`, `ttl_seconds`, `is_reregistration` flag
- `vessel.heartbeat` — after `heartbeat()` refresh
- `vessel.expired` — from `pruneExpired()` when TTL elapses

Fire-and-forget: registry mutations succeed unconditionally; bus failures rate-limited to one log per outage window. 2s HTTP timeout via `AbortSignal.timeout`.

**Tests:** existing 123/125 pass; 2 pre-existing failures unrelated.

**Live verification (09:14Z):**
1. WS subscriber connects to `wss://localhost:8080/ws`, authenticates
2. Test registration POSTed to `discovery-vessel:8100/register`
3. WS subscriber receives `{type: "vessel.registered", data: {vessel_id: "test-vessel-2", source_vessel_id: "discovery-vessel"}}` within ~50ms

The bus is live. Any vessel can now subscribe to vessel-topology changes by connecting to the existing WS endpoint and filtering on `type === "vessel.registered"`.
