## §4 — Ingestion mechanism

The brief enumerates (a) one-shot, (b) chokidar watcher, (c) git hook, (d) systemd timer. Per substrate-direction (CLAUDE.md memory `project_deployment_direction_2026_05_23`: kubectl/Helm suspended, container-local everything), and per the substrate's existing pattern of systemd units (`scripts/substrate/units/*`), **(d) systemd timer** wins:

- (a) operator-cadence — findings can sit a week before ingestion. Defeats the L4 closure point.
- (b) chokidar — adds a long-running daemon to the substrate just to watch one file. Polling at 5-min cadence has equivalent latency for prose-edited markdown.
- (c) git hook — fires only on `git commit`, but findings land via `Edit` tool calls on operator-floor files that are sometimes uncommitted for hours. Misses the very gap-window we're trying to close.
- (d) systemd timer at `OnUnitActiveSec=5min` — mirrors `boredom-vessel` cadence (CLAUDE.md §6), bounded latency, no daemon, runs in-container, restartable, dies cleanly. Idempotent so re-runs are safe.

**Decision: (d) systemd timer**, mirroring `boredom-vessel.timer` exactly.

## §5 — Classification: substrate_authorable vs operator_required

The brief asks: parse classification from prose, or have audit emit it as frontmatter? Per the verified Finding header pattern (`§2`), severity is already in the heading. Remediation class is **not** in the heading or any structured field today.

**Recommendation**: the bridge does NOT do LLM-classification. Instead:

1. **Bridge extracts severity** deterministically from `(<SEVERITY>)` in the heading. ~3 LOC regex.
2. **For pre-existing F1–F23**: the bridge emits with `classification_metadata.remediation_class: "unclassified"`. The substrate's downstream closer (iter-031) or a small `classify-finding` activity assigns the class as a separate concern. Don't block ingestion on classification.
3. **For future findings**: extend the canonical Finding header with a third paren-group:
   ```
   ## Finding 24 (HIGH, operator_required) — <title> (<ts>)
   ```
   Bridge reads it deterministically. Audit-side overhead: one extra token per heading. ~5 LOC regex extension.

This avoids LLM-in-the-bridge entirely — the bridge stays a ~125 LOC deterministic parser. The audit subagent (LLM, already operating) does the classification at write-time, where it has full context. **Cleanest separation.**

## §6 — Idempotency / dedup

Primary key: `gap.id = "F<N>-<slug>"` (e.g., `F22-vessel-heartbeat-silent`). Slug derived from heading title, lowercase, kebab-case, first 4 words. Stable across re-runs because `N` and title don't change post-publication.

Looking at `substrate-gap.ts:96-100` (the write handler reads existing gaps from JSON, the resolver pattern), UPSERT semantics need verification but the file-backed store at `WORKSPACE_ROOT/gaps/gaps.json` (L84) is a flat array — the bridge can implement dedup client-side by reading the substrateGap read-pointer first and only POSTing diffs:

1. `GET` via `substrateGap` read-pointer with `category: "missing_idiom"`, `source: "operator_narration"` → existing gap set.
2. Parse `audit.md` → desired gap set.
3. For each parsed finding: if `id` not in existing set, emit `substrateGap_write`. If `id` exists but heading severity changed, emit update (only if status still open).
4. For each existing gap whose `id` no longer appears in audit.md AS OPEN (e.g., F8 retracted, F22 closed): emit `substrateGap_write` with `status: "closed"` or `"rejected"`. **Detection**: scan heading for `~~strikethrough~~` (F8) or "CLOSED" markers (F22 per iter-077).

The bridge becomes a **reconciler**, not an emitter. Same model as Kubernetes controllers. Idempotent by construction.
