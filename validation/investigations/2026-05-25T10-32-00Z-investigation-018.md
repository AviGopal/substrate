## Finding A (corrected) — concept-db seeder fails on SurrealDB schema, not on missing route

The seeder POSTs to `/concepts` with `{source_type, shape, content}`. Inside the container concept-db answers — the route exists at `routes/concepts.ts:40` (`concepts.post('/')`), mounted at `index.ts:84`. The 400 response body is:

```
Query failed in activity-system.learning_loop:
  Expected a record<concept_q2fCxRCkap6S> but cannot convert 'concept' into a record<concept_q2fCxRCkap6S>
```

Some field of type `record<concept>` (the schema defines three: `concept_edge.from_concept`, `concept_edge.to_concept`, `concept_usage.concept_id`) is receiving the string `'concept'` instead of a record id. The seeder payload itself does not reference these fields directly, so the create handler must be writing them internally (likely seeding initial edges or usage rows during create). The randomized-suffix table name (`concept_q2fCxRCkap6S`) suggests a transient/aliased table from a query path. The fix lives in the create handler, not in the seeder.

The seeder's information-loss is still a real understandability bug: `seedConcept()` at `seed-concepts.ts:188-197` returns `boolean` and discards the status, body, and URL. The next operator to look at this had to do a 30-minute archaeology dig (this investigation) instead of seeing `[seed-concepts] ERROR vessel_discovery_registration: 400 - record<concept> mismatch` once. **This pattern likely exists in other seeders** — worth a sweep of `scripts/substrate/` and `/vessels/*/scripts/seed-*` for boolean-return error swallowing.

## Addendum — Concept-db as conditioning layer (generalizability / specificity / conditionality)

Background subagent #2 (full transcript: `/tmp/.../a7624d8a0cec28a7a.output`) extended Framings 1–3 along three orthogonal axes.

**The reframe:** retrieval is not "content similarity" but **context-bound applicability** — a concept either applies at the present invocation or it does not, and concept-db's job is to make that decision well. The three axes are a control surface, not three independent dimensions.

**Generalizability** — today's only levers are `concept.shape` (`sql/core/001-concept-tables.surql:19`) and `concept_edge.edge_type ∈ {derived_from, example_of}` (`:96-97`). Missing: per-context outcome bucketing on `concept_usage` (`:130-131`). All outcomes are currently averaged into a single relevance scalar — over-generalization is invisible because there is no `(concept_id × consumer_shape)` view. Probe: shape-bucketed retrieval beats global α/β posterior on `create-shape-provider-goal`.

**Specificity** — supported via `scope ∈ {global,org,project}` (`:59-61`), `source_type` priority gradient (CLAUDE.md table), opaque `pointer` (`:18`). Missing: `operator_id`, `specificity_class ∈ {directive, preference, observation, hypothesis}`, expiry. The retrieve→inject→consume pipeline drops specificity at injection — the LLM resolver has no protocol for marking a concept as a hard directive. Probe: one operator-scoped concept against the 12-template boredom rotation; observe whether the next 5 dispatches respect it.

**Conditionality** — schema offers essentially nothing. Today's "conditionality" lives in TypeScript callers passing filter args to `concept_search`. Missing: `concept.preconditions: array<{key, op, value}>` evaluated AND against caller-supplied context. **This is the load-bearing gap** — the other two axes are special cases of "no preconditions field." Minimum viable form is structural (equality / membership / shape-subset), not a DSL. Probe: attach `precondition: minutes_since_last_coverage_tick ≥ 20` to a `coverage-tick` concept; observe whether the rotation gate flips off 12-template churn.

**Unified read:**
- Generalizability without specificity = over-eager LLM (every concept fires everywhere).
- Specificity without generalizability = operator-rote (nothing transfers).
- Conditionality is the interface that makes the trade-off **operator-tunable**: a globally-scoped concept with strict preconditions behaves locally; a project-scoped concept with empty preconditions behaves like a fallback.

**Artifact placement on the cube:**

| Artifact | Generalizability | Specificity | Conditionality | Today |
|----------|-----------------|-------------|----------------|-------|
| Recipe / template | High | Low | Low–Med | In activity-api; concept-db link missing |
| Playbook | Medium | Medium | **High (failure_mode)** | Essentially absent |
| Personal detail | Min | **Max** | Low | Partial via `source_type=human_input`; no `operator_id` |
| Note | Variable | Variable | Variable | Flattened by missing `specificity_class` |
| Introspection trace | High *post-evidence* | Med | High | Dangerous without per-context outcome bucketing |

**Two gaps dominate:** (1) `concept_usage` needs per-context outcome bucketing — without it, generalization has no statistical floor. (2) `concept` needs any per-row guard expression — every other axis-gap is a special case.

**The single highest-leverage audit observation to make next:** for the next 100 LLM-resolver invocations that retrieved ≥1 concept, does the resolver's output behaviour change in any operator-detectable way vs. the same invocation replayed with retrieval disabled? If rarely, concept-db is a memory store, not a conditioning layer, and the entire framework collapses to Framing 1. If often, and the change correlates with `specificity_class`, conditionality-as-tuning-surface is the right frame and the two schema gaps above are the next investment.

This observation requires a replay infrastructure that does not exist yet. The cheap proxy: instrument `concept_consumption` impulses (Framing 1's write) with both the retrieved concept set and the resolver's verdict; over time, A/B on the natural variation when retrieval returns empty (concept-db is empty today — there's free baseline data sitting in F-036's 60+ failures right now).
