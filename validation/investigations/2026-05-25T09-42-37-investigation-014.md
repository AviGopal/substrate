### 5605057b — Iteration-24 narration (Thompson RETURN fix context)

This narration-only commit explains the "RETURN fix" that landed in `c48c4333`. The issue:
SurrealDB 3.x rejected the object shorthand syntax `RETURN { id, total_executions }` in
`execution-traces.ts`. The `applyOutcomeToPosteriors` callback never fired because the RETURN
statement threw a parse error silently. Fix: changed to explicit RETURN syntax. Effect: Thompson
posteriors now increment on every trace outcome.

topology goals are buried under generated tasks and never reach execution.

**F-topology-queue**: The `topology_harness_next` Redis key exists but topology templates are not

### 67bbcdb6 — VesselId/endpoint uniqueness fix (SIGNIFICANT)

Both development-vessel and concept-db were inheriting `VESSEL_ID=substrate-local` and
`VESSEL_ENDPOINT=http://127.0.0.1:8080` from the global `/etc/substrate/env` file. When both
vessels registered with the discovery registry, they used the same `vesselId` and overwrote each
other. concept-db won the last heartbeat, leaving development-vessel's 30 shapes invisible.

Fix: added per-vessel `Environment=` overrides in each `.service` unit:
- `development-vessel.service`: `VESSEL_ID=development-vessel-local`, `VESSEL_ENDPOINT=http://127.0.0.1:8090`  
- `concept-db.service`: `VESSEL_ID=concept-db-local`, `VESSEL_ENDPOINT=http://127.0.0.1:8260`
- `gen-env.sh`: removed the global `VESSEL_ID` and `VESSEL_ENDPOINT` lines

**Verified impact**: discovery registry now shows 5 distinct vessels with 54 shapes. development-vessel
running since 09:35:54Z, registered. concept-db running since 09:35:52Z, registered as
`concept-db-local`. F-050 is resolved.

## create-shape-provider-goal: Regression Root Cause Identified

The validator's "24%→0% regression" is explained by a structural change in how the activity is
dispatched. Examining composition chains in the traces:

```
exec_476s6blt: coverage-tick            SUCCESS  dur=44122ms  tasks=0  parent=None
  exec_f0g1bo5l: validator-dispatch     SUCCESS  dur=43664ms  tasks=0  parent=coverage-tick
    exec_y5qzn92w: slot-binding         SUCCESS  dur=36376ms  tasks=0  parent=validator-dispatch
      exec_5etnnwlg: create-shape-provider-goal  FAIL  dur=1ms  tasks=0  impulse_count=0
```

create-shape-provider-goal is dispatched as a **child** of slot-binding with `impulse_count=0`.
No impulses are passed down the composition chain. The activity requires input shapes
(activity_metrics, activity_template, goal, execution_trace, etc.) that are never provided.
It fails in ~1ms before executing any task.

Prior to the RETURN fix + vesselId fix, create-shape-provider-goal was dispatched at the top level
(direct boredom dispatch) with some impulses present. That explains the historical 24% success rate.
Now it's nested 3 levels deep with empty impulse pool.

F-036 root cause updated: **composition dispatch provides no impulses to create-shape-provider-goal**.
The activity_recommendation resolver is registered but never called because the activity fails the
slot-binding phase before any task executes. This is an impulse propagation gap in the composition
chain, not a resolver issue.
