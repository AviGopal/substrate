### F-128 (LOW) — consecutive_progressing_cycles semantics misleading → VERIFIED CLOSED

**Fix:** dev-vessel `9d318bb` renames the primary field to `consecutive_windows_with_new_shapes`, retains `consecutive_progressing_cycles` as a backward-compat alias, and adds `consecutive_windows_max`.

**Live verification (2026-05-27T17:15Z):**

```
POST http://127.0.0.1:18090/v2/impulses/resolve
{"impulse":{"pointer":{"type":"coverage_tick","num_windows":4}}}

→ consecutive_windows_with_new_shapes: 0
→ consecutive_windows_max: 4
→ consecutive_progressing_cycles: 0   (alias, same value)
→ coverage_progress: True
→ coverage_fraction: 0.235
→ total_advertised_shapes: 34
→ total_learned_unique: 8
```

All three fields present. `consecutive_windows_with_new_shapes=0` on this probe despite `coverage_progress=True` — this is expected: `coverage_progress` checks whether *any* of the most recent ⌈N/2⌉ windows introduced a new shape (weak condition), while `consecutive_windows_with_new_shapes` requires the *newest* window to have introduced shapes (strict condition). The two metrics measuring different things is by design.

**Note on probe format:** The investigation brief used `{"impulse":{"type":"coverage_tick","pointer":{"type":"coverage_tick"}}}` which returned all MISSING values. That format triggers a validation error in dev-vessel's route handler (`pointer.type is required` — the handler expects `body.impulse.pointer.type`). The correct format is `{"impulse":{"pointer":{"type":"coverage_tick"}}}`. The brief's probe was defective; the field implementation is correct.
