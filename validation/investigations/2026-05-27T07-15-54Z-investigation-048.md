## F-123: coverage_progress Criterion — Structural Guarantee Confirmed

**Status: OPEN** (confirmed by source code inspection)

The critical question from the investigation-047 prompt was: are the coverage-tick windows independent queries or cumulative queries? The source code answers definitively.

From `/vessels/development-vessel/src/resolvers/coverage-tick.ts` (lines ~120-127):
```typescript
for (let i = 1; i <= numWindows; i++) {
  const since = new Date(now - i * windowSize * 1000).toISOString();
  const counts = await computeCountsForWindow(since, auth, allTemplates);
  cells_over_time.push(counts);
}
```

`computeCountsForWindow(since, ...)` fetches all traces with `executed_at >= since`. This means:
- `cells[0]`: traces since `now - 1h` (last 1 hour)
- `cells[1]`: traces since `now - 2h` (last 2 hours, **includes all of cells[0]'s data**)
- `cells[2]`: traces since `now - 3h` (includes cells[0] + cells[1] data)
- `cells[3]`: traces since `now - 4h` (includes all data from all shorter windows)

By construction, the set of traces in window `i+1` is a superset of window `i`. Therefore `reachable_learned[i+1] >= reachable_learned[i]` always. The monotonicity check `curr.reachable_learned > prev.reachable_learned` (where `curr` is the older/longer-lookback window) is satisfied whenever:
1. Any template is executed at all (adding learned shapes to the longer windows), AND
2. The template coverage doesn't perfectly plateau exactly at the same shapes in all windows.

The live data confirms the structural guarantee: `RL = [7, 9, 10, 11]` newest-to-oldest. The strictly-increasing check is `True` as guaranteed. `coverage_progress = True`.

**What this means for S.4a lift criterion integrity:** `coverage_progress=True` cannot distinguish between:
- "The substrate is genuinely expanding its execution coverage of new shapes over time" (the intended signal)
- "The substrate has any executions at all" (the trivially-achievable state)

For `coverage_progress` to become `False`, shapes would have to appear in newer windows but not older ones — which would require traces to be deleted or TTL to expire, neither of which is happening. In practical terms: once `reachable_learned` in any window exceeds 0, the criterion will remain `True` indefinitely regardless of whether actual coverage is expanding or contracting.

The 1h window absolute value did improve from 5 (inv-047 at 05:21Z) to 7 (inv-048 at 07:24Z). This is real — more diverse templates were executed in the last hour than previously. But `coverage_progress=True` would report identically even if the 1h window had declined from 7 to 3.

## What Would Fix the Critical Path

The two highest-impact changes to make S.4a meaningful:

1. **Fix F-123 (coverage criterion):** Restructure coverage-tick to use rolling windows anchored at fixed points (e.g., compare "last 1h" vs "1h-2h ago" as independent, non-overlapping windows). Or replace with a direct measurement: what fraction of advertised templates have at least one execution trace in the last 24h? This is not gameable by cumulative inclusion.

2. **Fix F-124 ({{}} interpolation in probe):** The probe task[1] needs to either: (a) use an llm resolver to extract the top shape and pass it downstream, or (b) use a single resolver that internally combines get-report + recommend logic (as commit 6c3448e attempted before being reverted).

Without these, the coverage criterion is not a valid lift gate.
