## Substrate Self-Development: F-093

Between 17:00Z and 17:03Z (PDT), the substrate's devbob agent committed 5 fixes in a rapid burst. Three are operationally significant:

### Fix 1: coverage-tick trace fetch limit 200→2000 (b39db49f / 84638bb)

The coverage-tick resolver was fetching execution traces with `limit=200`. With validator-dispatch alone running at ~300 traces/hour, 200 traces covers only ~40 minutes of history. The client-side time filter (`ts >= since`) works correctly — but when all 4 time windows fetch the same 200 most-recent traces, the 2h/3h/4h windows pass all 200 through their broader filters while the 1h window filters down to fewer traces. This produced the phantom pattern: rl[0]=9 (1h window, fewer traces) vs rl[1-3]=11 (all windows seeing same ~200 traces).

With `limit=2000`, each window fetches a 6-hour slice and applies its time filter correctly. The temporal variation is now real.

**Commit message (substrate authored):** "At ~300 validator-dispatch traces/hour, limit=200 captured only ~40min of execution history. All 4 time windows saw the same 200 traces and reported identical rl counts (spurious plateau). With limit=2000 the resolver now shows real temporal variation."

**Deployed:** Confirmed. `docker exec substrate-live grep -n 'limit=' /vessels/development-vessel/src/resolvers/coverage-tick.ts` → line 45: `limit=2000`. The development-vessel restart at 23:39:47Z was a sync of this fix.

### Fix 2: boredom explicit template goals (71960aff)

Boredom's abstract goals ("measure the substrate topology and report coverage progress") were being matched by the LLM's `compose_goal` step to high-alpha templates — validator-dispatch (α=3759) and slot-binding (α=534) — producing only 3 unique output shapes in each hour window (activity_template, patch, analysis). This made `reachable_learned_strictly_increasing` impossible: the 1h window and 2h window always saw the same 3 shapes.

The fix rewrites boredom goals to name templates explicitly:
```
OLD: "measure the substrate topology and report coverage progress"
NEW: "run the coverage-tick activity to measure substrate topology coverage and emit a coverageReport"

OLD: "run the full topology discovery chain and emit a coverage report"  
NEW: "run the substrate-health-tick activity to check vessel health and emit a substrateHealthReport"
     "run the harness-check-scenario activity to validate a failure-mode scenario from the harness matrix"
     "run the add-resolver-to-vessel activity to register any missing resolver capability discovered in the last harness run"
```

**Deployed:** Confirmed. `docker exec substrate-live journalctl -u boredom-vessel.service` at 00:03:19Z shows: `submitting goal[0]: "run the coverage-tick activity to measure substrate topology coverage and emit a coverageReport"`.

### Fix 3: boredom 8-minute AbortSignal (eb179580)

Bun's default socket timeout was causing ~36% of boredom ticks to abort with SIGTERM at 5 minutes. Goals that use LLM resolvers (topology chain, probe-unlearned-shapes) need up to 7-8 minutes. A single line addition of `signal: AbortSignal.timeout(8 * 60 * 1000)` to the goal-host fetch call.

**Deployed:** Confirmed via boredom completion rate: observation window (22:00Z-00:05Z) shows ~92% completion vs 64% at investigation-026.

**Diagnosis quality assessment:** The substrate's commit messages describe both root causes in language matching the auditor's independently-derived analysis. This is the highest-quality autonomous self-diagnosis observed across 27 investigations.
