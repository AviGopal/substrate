## F-037 — the learning loop is decoupled

The most interesting new finding. Querying coverage-tick's
template detail returns:

```json
{
  "total_executions": 68,
  "successful_executions": 60,
  "failed_executions": 8,
  "success_rate": 0,
  "thompson_alpha": 1,
  "thompson_beta": 1,
  "total_selections": 0
}
```

Two things are wrong:

1. **success_rate=0** when successful_executions=60 and
   total_executions=68. Math says 60/68 = 0.88. Either the
   field is not computed, or it's computed from a different
   numerator/denominator than its name suggests.

2. **thompson_alpha=1, thompson_beta=1**: the uniform Beta(1,1)
   prior. If the substrate had been updating posteriors from
   the 68 executions (60 successes, 8 failures), Thompson
   parameters should be at approximately α=61, β=9. They are
   unchanged at the prior.

The substrate IS executing coverage-tick (68 times). The
substrate IS counting executions. But the substrate is NOT
moving the Thompson posteriors that should learn from those
executions. The selection layer reads from Thompson posteriors;
if posteriors don't move, the substrate cannot prefer
better-performing templates over worse-performing ones over
time.

This is the structural learning failure underneath the
boredom-loop's stagnation. Even if F-024 (boredom timer using
goal-text) is fixed, even if F-028 (binding broken) is fixed,
the substrate STILL won't learn from successful executions
because the Thompson update path is decoupled from outcome
data.

This finding probably needs dev investigation: is there a
write path bug, a serialization bug, or a code path that
counts executions separately from Thompson updates?
