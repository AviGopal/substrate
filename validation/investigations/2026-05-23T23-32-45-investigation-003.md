## New findings

### F-014 (medium) — F-V58 embedding fix not in effect on runtime

`curl -sf http://localhost:18080/health | jq '.checks.embedding'`
returned `{ status: "disabled", model: "all-MiniLM-L6-v2", dim:
384 }`. Memory entry: "F-V58 fix (2026-05-18): EMBEDDING_MODEL_DIR
env was missing from Dockerfile runtime stage, causing
embedding.status=disabled on all pods since Phase 18.5; fixed in
1.20.9-66fb99c."

Live version reports `1.20.9` without commit suffix. The fix
either isn't in this build, or `EMBEDDING_MODEL_DIR` is unset on
the systemd unit. Documentation claims the fix is shipped;
runtime says otherwise.

This is the cleanest possible demonstration of the auditor's role:
**memory and CLAUDE.md cannot prove the substrate is running with
the fix. Only the substrate itself can.**

### F-015 (low) — `total: -1` sentinel on trace list endpoint

`/v2/activities/execution-traces` returns `total: -1` in its
response envelope. Undocumented; downstream consumers expecting
a count get a negative number. Either compute the count or use
null; -1 as a sentinel is a bug.

### F-016 (medium) — Narrator paused

No substrate-narrator process running; last snapshot is ~1.5 min
old; no event JSONL file in `validation/observations/`. The
runtime-transient capture infrastructure is in place but not
actively running. Investigations after this one can only sample
momentary state via HTTP, not observe event streams over windows.

The narrator should be restarted as a background process. This
is itself a finding because the previous run produced only two

### F-017 (low, positive) — Ribosome is firing

Live trace dump returned a trace with `template_id:
"ribosome-extract"`, `metadata.reason: "lifecycle hook:
lifecycle:activity:postExecution"`, `success: true`,
`vessel_id: "substrate-local"`. This is positive evidence that
the lifecycle-subscription pattern + template-extraction path is

Important caveat: ribosome firing does not imply
ribosome-extracted templates are correct or load-bearing. It
only confirms the subscription path works. The quality of

### F-018 (low, positive) — Snapshot-vs-runtime consistency

The narrator's snapshot recorded 18 templates; live HTTP query
returned 18 templates. This is the simplest possible
runtime-transient consistency check, and it passed. The narrator

### F-019 (high) — Discovery-vessel rejects activity-api's API key

The snapshot recorded `discovery_vessel: { endpoint:
"http://localhost:18100", reachable: false, stats: null, error:
"HTTP 401" }`. The same `~/.metabob/config.json` apiKey that
authenticates to activity-api receives 401 from discovery-vessel.

This is a real operational divergence. CLAUDE.md says
identity-vessel is the single source of truth for authentication.
If both foundation vessels delegate to identity-vessel, they
should agree on whether a key is valid. They don't.

Likely cause: F-006 — hardcoded `metabob.com` defaults mean
discovery-vessel and activity-api may resolve "identity-vessel"
to different addresses depending on which env override is
present. Discovery-vessel's `auth.ts:63` defaults to
`https://identity.metabob.com`; activity-api may have a different
override active. The two ask different identity-vessels whether
the key is valid; the answers differ.

This is a structural finding. Until F-006 is resolved (via
`substrate-identity-resolution`), foundation vessels can have
inconsistent auth state on the same key.
