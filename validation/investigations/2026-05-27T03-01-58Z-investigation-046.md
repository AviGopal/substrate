### F-113: Coverage REGRESSED to nadir

Investigation-045 reported the following trend at 00:04Z: windows at 23:04Z=7, 22:04Z=7, 21:04Z=8, 20:04Z=8. The report described this as "stabilizing" with the targetTemplateId fix expected to drive recovery.

The current snapshot at 02:58Z shows: 01:58Z=6, 00:58Z=9, 23:58Z=15, 22:58Z=15.

Reading these windows in chronological order (22:58Z→23:58Z→00:58Z→01:58Z): the metric held at 15 for two windows in the late-26th period, then fell to 9, then to 6. The 6 value matches the prior nadir recorded in investigation-044.

An important clarification about the coverage metric discovered this investigation: the coverage resolver fetches a rolling window of traces (limit=2000, client-side time-filtered) and counts unique output shapes produced within each 1-hour window. This is **per-window learning intensity**, not cumulative. A window showing reachable_learned=6 means only 6 unique output shapes were produced by all executions in that hour. Given that validator-dispatch, slot-binding, and create-shape-provider-goal collectively emit no development-vessel output shapes (coverageReport, reachableUnlearnedReport, topologyGapReport, etc.), each hour dominated by these templates can only count shapes from the 5% of named-template executions.

The targetTemplateId fix ensures that when boredom fires a named-template goal (0,1,2,3,5,6), it reaches the correct template. But the coverage window that counts shapes is typically populated by the sub-executions within those named templates, plus any executor-layer overhead. A single 30-minute boredom cycle that routes correctly produces at most one named-template execution per window — insufficient to drive the metric upward when 95% of all traces produce no shapes.

### F-119: consecutive_progressing_cycles misleadingly high (NEW)

The coverage_tick at 02:58Z reports `consecutive_progressing_cycles=2` alongside `coverage_progress=false`. The four windows show a declining trend (15→15→9→6). These two values are inconsistent with each other if consecutive_progressing_cycles is meant to reflect the current snapshot.

The most likely explanation: consecutive_progressing_cycles is persisted from prior ticks where coverage_progress was true, and incremented/decremented based on historical calls, not recomputed from the current 4-window snapshot. The counter thus carries forward a stale signal.

This finding matters for lift-criterion integrity. If any future audit or automated check reads consecutive_progressing_cycles as a proxy for "the substrate has been making consistent progress," it would see 2 (suggesting progress) when the actual windows show regression to a new nadir. The coverage_progress field is the correct gate and it correctly reads false. The concern is defensive: a gameable criterion could be constructed from consecutive_progressing_cycles without coverage_progress, and this investigation documents the divergence before such a criterion is proposed.

### F-120: goal[4] poll budget exhaustion without outcome logging (NEW)

At 01:13:27Z, boredom fired goal[4]: "identify shapes in the execution graph that have no known producer and escalate the most critical one." This goal has no targetTemplateId — it is the open-Thompson slot where Thompson Sampling selects the template.

At 01:17:57Z (4.5 minutes later), boredom logged: "poll budget exhausted — goal continuing async, dispatchId=a9569388-03e2-4a74-b21b-1e80dc5aa7a5." The boredom unit then deactivated. No subsequent boredom log line records the execution ID or outcome for this dispatch.

The execution trace list shows draft-gap-closing-activity (exec_0bs97fii) with executed_at=2026-05-27T01:18:44Z and duration=315683ms (~5.25 minutes). Timing is consistent with this being the goal[4] execution (started 87 seconds after the poll timeout, completed at approximately 01:24Z). But the boredom log cannot confirm this, and the execution ID from the trace cannot be cross-referenced to the dispatchId from the log.

The finding is: **boredom has no mechanism to record the actual execution ID or final status of async-continuing goals**. This creates a gap between what boredom reports and what the trace store contains. It is less severe than F-110 (which involved a false report of success for a failed execution) but is a systematic observability gap for goal[4]-class dispatches.
