## Section A — How concept-db is *meant* to be used

Per `docs/architecture/IMPULSE_ACTIVITY_FOUNDATION.md:283-288` and `repos/concept-db/CLAUDE.md`: concept-db is a vessel in the four-primitive model. The seam with activity-api is **shape-based, not architectural**:

- **activity-api**: trace patterns, template Thompson posteriors, composition-edge α/β, impulse-relevance scores
- **concept-db**: concept usage counts, conceptGraph relationships, conceptSequence patterns

Both stores record rows tied to executions and feed Thompson posteriors. The seam: activity-api owns activity/trace shapes; concept-db owns concept-graph shapes. A concept *referenced from* a trace produces an `impulse_resolutions` row in activity-api AND a `concept_usage` row in concept-db — same event, two perspectives, no duplicate write (the observer is the only forwarder).

### Three canonical write paths (in design-intent order)

1. **Direct creation** via `POST /concepts` or `concept_create` MCP tool. Operator/human-authored — the cold-start path iter-020 endorsed.
2. **Cross-vessel passive recording** via WebSocket observer at `repos/concept-db/src/services/execution-observer.ts:383`. On `task.completed` events from activity-api referencing a `concept`-shape impulse OR an id beginning with `concept:` / `concept_`, the observer calls `recordUsage()` (`resolvers/usage.ts`). Populates `concept_usage` autonomously — no caller code needs to know concept-db exists.
3. **Upkeep activities** — five Thompson-Sampled self-mutation activities (`split-long-concept`, `resolve-island`, `adjust-priority-relevance`, `prune-irrelevant-neighbors`, `decay-stale-relevance`) on a 5-min scheduler. Mutate the graph as a function of itself.

### Three canonical read paths

1. **Pointer-type resolver dispatch** (`concept-db/CLAUDE.md:152-178`): impulses with `pointer.type === "concept"` route to concept-db's `concept_resolve`. **This is the canonical landing point for Cα/Cβ from iter-022** — pre-interpolation injection at `llm-prompt.ts:85` consumes this resolver.
2. **Discovery-routed shape queries**: any vessel posting an impulse-resolve for one of the 8 read shapes (`relatedConcepts`, `conceptUsageStats`, etc.) gets routed through discovery → concept-db `/resolve`.
3. **MCP tool calls**: `concept_search`, `concept_neighbors`, `concept_sequence_record` invoked by MCP clients (standalone-product surface), not by activity-api.

## Reframing under the neutral-emitter principle

The principle: **emitters broadcast neutrally; consumers register the hooks they need.** No event is "for" a specific consumer. Under this principle the original "by design" verdicts on items 3 and 4 are themselves defects:

- **Item 3** (concept-db's internal events trapped in in-process EventEmitter): the dispatcher should be a broadcast transport. Any vessel that wants to react to `concept:created` — ribosome, audit-vessel, future analyzers — should be able to subscribe. Today no one can. The "internal-only" status is a missing broadcast bus, not a design feature.

- **Item 4** (activity-api's `lifecycle:task:*` events not consumed by concept-db): the events flow on a channel structurally coupled to workbench. If concept-db has any use for task-level lifecycle (e.g., recording concept usage tied to specific task transitions or pre-binding decisions, not just `task.completed`), it should be free to subscribe. The fact that the channel makes that impossible is the defect.

The validator's gap-001 — which asserted "concept-db missing lifecycle integration" — was correct by the neutral-emitter principle. My earlier dismissal of it as "using the wrong consumer model" was the wrong framing.

This implies a substrate-spanning audit finding: **every lifecycle event in the substrate should be on a neutral broadcast channel.** The `task.completed` WS channel that concept-db already consumes is the right shape; the `lifecycle:task:*` workbench channel is the wrong shape. Either the latter migrates onto the former's transport, or both consolidate onto a single substrate event bus.

## The substantive gap that remains: no concept-extraction-from-trace path

Of the three canonical write paths, only #1 (direct creation) and #3 (self-upkeep) work without prerequisite data. #2 (observer passive recording) requires concepts to already exist for `recordUsage` to fire — otherwise `extractConceptRefs` returns empty.

**There is no automated path from a trace into a concept-write.** Ribosome does templates; no sibling does concepts. The `extract-pattern` + `concept-from-pattern` activities listed in CLAUDE.md are ROADMAP. The dedicated seeder (`concept-db-seeder.service`) is `failed`. The table is empty.

This means: even with iter-022's schema fixes landed (concept-db is *writable*), and even with iter-025's envelope design ready, **the substrate has no autonomous mechanism to populate concept-db from execution evidence.** Operator-authored writes (Cα/Cβ) are the only realistic seed source today. The "concept-db learns from traces" promise lives in roadmap-state.
