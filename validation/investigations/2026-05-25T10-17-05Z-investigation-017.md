## Finding A — concept-db is empty (24/24 seed concepts failed on startup; cause is a route mismatch the seeder swallows silently)

**What the substrate believes about itself:** concept-db.service is `active running`; `GET /health` returns `{status:"healthy",circuitState:"CLOSED"}`; discovery registry advertises it as a healthy vessel.

**What is actually true:**
- `concept-db-seeder.service` exited 1/FAILURE at substrate start (09:03:39Z). Journal shows `[seed-concepts] done: 0 seeded, 24 failed`.
- Direct probe: `POST http://127.0.0.1:8260/concepts` → `404 Not Found`. `GET /concepts/search?source_type=...` → `404`.
- The 24 seed concepts the seeder tries to write all target `/concepts`, which concept-db does not serve.
- `seedConcept()` in `/vessels/seed-concepts.ts:188-197` returns `boolean` only (`res.ok || res.status === 409`). The HTTP status, response body, and target URL are discarded. The caller logs `WARN failed to seed <shape>` with no further context.

**Why this matters from a resolver's POV:**
Any task whose resolver depends on `relatedConcepts`, `conceptUsageStats`, or any other concept-db shape will get an empty result. The resolver cannot distinguish *"empty because the substrate has no concept for this shape yet"* from *"empty because concept-db's mutation surface is broken and was empty from boot"*. The trace records `success: true` on the task either way (the resolve call did return successfully — it returned nothing).

**Cascade into F-036:** see Finding B.

**Suggested activity to close this understandability gap:**
A `vessel-resolver-contract-probe` activity that, after a vessel registers in discovery, fires one POST against each advertised mutation shape with a synthetic payload and confirms the endpoint returns ≠404. Emits `vesselContractDriftReport` impulse on mismatch. Lifecycle hook: subscribe to `lifecycle:vessel:registered`. This would have caught concept-db at boot and emitted a high-severity drift report instead of `WARN failed to seed`.
