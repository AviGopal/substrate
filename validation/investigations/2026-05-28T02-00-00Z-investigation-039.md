# Investigation 039 — How impulses match resolver arguments + the recursive-authoring substrate property

This investigation has two parts. Part 1 grounds the impulse-to-resolver matching mechanism end-to-end (the prior turn's content, codified for the investigation chain). Part 2 addresses the operator's just-asserted substrate property: **for any state space signature, the substrate should work toward resolving every goal, creating functionality as needs are discovered, including validation activities that learn what success looks like.**

## Part 1 — The matching mechanism (six layers)

### Layer 1: Declaration (template-author time)

Each task declares its shape contract via `repos/ias-executor-ts/src/ontology.ts:46-47`:
```typescript
inputShapes?: (string | InputShapeRef)[]
outputShapes?: string[]
```

`InputShapeRef` at `:29-36` supports `{shape, cardinality: "any" | "all" | "exactly_one", producedBy?: {resolver_id, template_id, vessel_id}}`. Provenance narrowing is the maximum-specificity contract.

For LLM tasks: `prompt.template` with `{{shape_x}}` placeholders + `prompt.variables`. For non-LLM tasks: `config` with resolver-specific parameters (which may themselves carry `{{shape_x}}` interpolation).

### Layer 2: preBinding lifecycle (subscribers resolve ambiguity)

`engine.ts:84-94` before each task computes `missingShapes` and emits `lifecycle:task:preBinding` with `{inputShapes, currentImpulseShapes, missingShapes, variables, parentDepth, parentGoalText}`. Post-iter-028 C, the engine awaits subscribers via `eventSink.flush` at `:126`.

Subscribers (slot-binding meta-activity, validator-dispatch, future concept-db autonomous-read) react:
- Pool population — inject impulses via lifecycle write
- Producer dispatch — query `discover-by-shapes backward` for missing-shape's producer; spawn sub-goal via `create-shape-provider-goal`
- Disambiguation — pick which instance for slots with cardinality<=1 and multiple candidates (today: first-match-heuristic per iter-027)

### Layer 3: resolveInputs (hard contract enforcement)

`engine.ts:450-478`. Filters pool by declared shape + `producedBy` constraint, applies cardinality. **Hard throw at `:465-467`** if any declared shape has no candidate. Returns selected impulses as `context.inputImpulses`.

### Layer 4: Resolver consumption (two patterns)

**(A) Interpolation pattern** (LLM-prompt, iteration's inner config): per `llm-prompt.ts:89-96`, declared inputImpulses merge into variable namespace by shape; `{{shape_x}}` resolves to `imp.content`. Match by shape name; first-match if multiple.

**(B) Config-driven pattern** (bash, file, impulse-resolve, validation, learning-signal-writer): resolver reads `task.config.<field>`; config can carry `{{shape_x}}` interpolation. Impulse-resolve's `config.pointer` dispatches via discovery to vessel-routed shape resolver.

### Layer 5: Vessel participation (discovery routing)

`impulse-resolve` dispatches to whichever vessel advertises the pointer's `type`. Discovery-vessel's registry IS the routing table. Cross-vessel content arrives via a deterministic prior task in the activity graph; the LLM consumes the already-present impulse.

### Layer 6: Disambiguation (what happens with multiple matches)

Today: **first-match-heuristic**. The relevance learning that SHOULD inform "which instance is best" (`impulse_relevance_metrics` per Foundation §533-554) is empty for non-opted-in templates (Finding 8 #2). `producedBy` narrowing in the template is the only operator-side workaround.

**The mechanism is real and operational at every layer; the intelligence about disambiguation is partial.** Adding the four missing pieces turns "match by shape, first-match" into "match by shape, pick best per learned relevance."

## Part 2 — The substrate property: resolve any goal by authoring what's needed

The operator's assertion: **for any conceivable state space signature (usually involving at least one goal), the substrate should work toward resolving every goal, creating functionality as needs are discovered, and creating validation activities to learn what expectations to have.**

This is a much stronger property than current substrate behavior. Today the substrate:
- Refuses on `primitive-shape` gaps (no producer anywhere → escalate)
- Refuses on cold-start promote (K=0 → reject)
- Refuses on missing-resolver (registry incomplete → throw)
- Confabulates or fails on synthesis ambiguity (no `unable_to_synthesize` channel)

Under the operator's framing, ALL of these should resolve to **author the missing piece** rather than refuse:
- `primitive-shape` → author a new producer template (via improvise→ribosome-extract per the prior turn) OR forge a new vessel via `forge-vessel-for-shape`
- Cold-start promote → bias toward exploration (the autonomous promoter's existing posture)
- Missing-resolver → author a new resolver (via `add-resolver-to-vessel`)
- Synthesis ambiguity → author a clarifying activity that produces the missing input

### What the substrate needs to author per gap-type

Cross-referencing iter-023's 7-type gap taxonomy with the substrate's authoring primitives:

| Gap-type | What to author | Existing primitive | State |
|----------|---------------|-------------------|-------|
| `missing-resolver` | New resolver in existing vessel | `add-resolver-to-vessel` template | In registry per iter-034 (untested) |
| `missing-vessel-attachment` | Retry via discovery routing | (transport, not authoring) | — |
| `missing-shape-in-pool` (producer known) | Sub-goal dispatch | `create-shape-provider-goal` | Shipped; 0% success in iter-034 window |
| `primitive-shape` (no producer anywhere) | New producer template OR new vessel | `improvise → ribosome-extract` OR `forge-vessel-for-shape` | Improvise+ribosome aspirational per prior turn; forge 1/12 success |
| `shape-ambiguity` | (selection, not authoring) | slot-binding heuristic | First-match today |
| `synthesis-failure` | Clarifying activity producing missing input | LLM output with `authoring_proposals` block (aspirational) | Not wired |
| `scope-exhaustion` | Operator escalation OR depth-cap relaxation | (operator territory) | — |

**The pattern under the operator's framing**: every refusable gap-type has an authoring primitive. Today most have it shipped or in roadmap; what's missing is the GLUE that turns gap-detection into authoring-dispatch.

### The validation-companion requirement

The operator's second clause: "creating validation activities to learn what expectations we should have."

This is the qualitative leap. When the substrate authors capability X, it doesn't know if X actually works correctly — it knows X is syntactically valid (Zod), but not whether its claimed `output_shapes` are semantically what it produces. The Goodhart concern from iter-031 (capability authored to pass replay-recall but fail paraphrase-recall) lives here.

Authoring a VALIDATION COMPANION addresses this:
- When `make-activity` (or `improvise→ribosome-extract`) authors capability X with declared `output_shapes: [Y]`...
- ...it ALSO authors capability `validate-X` whose job is "given an instance of Y, verify it's semantically what X claimed to produce."
- Both X and `validate-X` go through promote-gate.
- The substrate runs X, then runs `validate-X` on X's output, and credits or debits both based on agreement.

This is essentially **test-driven capability authoring** at the substrate level. The substrate's confidence in its own capabilities becomes graded by self-verification rate.

### Existing primitives that compose into this

- `validator-dispatch` template — runs validators on task outputs (per iter-028 B grounding). Currently dispatches OPERATOR-AUTHORED validators per declared rules in `task.config`. Extension: when capability X is authored, `validate-X` is authored as a paired template using `validator-dispatch` patterns.
- `goal_verification_labels` table (migration 101 per CLAUDE.md) — accepts high-confidence automated labels and human verdicts. The oracle corpus for "does this trace actually solve its claimed goal."
- `failure_mode` taxonomy on traces (per CLAUDE.md F-V56 / F-V57 grounding) — the 5-type discrimination already supports `verifier_negative` for "validator disagreed."

The mechanism is there; the **pairing of capability-authoring with validator-authoring** is not. `make-activity` produces a template; it doesn't produce a paired validator.

## Part 3 — How this shapes activity composition

### Composition becomes recursive expansion, not just selection

Today: a goal arrives; recommend ranks candidate activities by signature; the winner is dispatched.

Under the operator's framing: a goal arrives; recommend either finds a satisfying activity OR identifies that no activity satisfies; in the second case, **the substrate authors a new candidate via improvise→ribosome-extract** (per prior turn) and continues until either it converges or hits scope-exhaustion.

The activity graph stops being a fixed-at-template-author-time structure and becomes a **dynamically-expanding graph**, with new nodes added in response to gaps. Foundation §807-818's `Reachable` and `Unknown` states aren't permanent — `Unknown` becomes `Reachable` by authoring.

### The implications for the composition graph's shape

iter-034's catalog observation showed the substrate's graph is "a wide star with `goal` and `activity_template` as twin hubs, surrounded by orphan-producer leaves" — only ~3 two-hop chains exist. Under recursive expansion:

- Goal-driven authoring fills in two-hop chains specifically because the goal needs them. Random boredom probes can't.
- Orphan-producer terminals (`analysis`, `patch`, `commandResult`) get consumed when downstream activities authored to use them land.
- Named topology holes (`gapScenario`, `learnedTopologySnapshot`, `unknownShapeReport` per iter-034 §4) get producers as needed by goals that consume them.

**The composition graph's shape becomes goal-shaped over time**, not topology-discovery-random. The substrate's accumulated capability matches the substrate's actual usage rather than its operator's prior guesses about what would be needed.

### The implications for topology discovery

Foundation §820-833: "The impulse-activity loop is not a recipe executor. It is a topology discovery engine."

Under recursive-authoring, topology discovery has TWO modes:

| Mode | Trigger | Mechanism |
|------|---------|-----------|
| **Random exploration** | Boredom timer | Probe activities (coverage-tick, harness-run-matrix) walk unexplored regions; high coverage but low specificity |
| **Goal-driven authoring** | Goal arrives needing a capability that doesn't exist | Improvise→ribosome-extract or make-activity or forge-vessel-for-shape; high specificity but coverage limited to what's been asked |

Today's substrate runs mostly mode 1 (boredom probes random) and minimally mode 2 (because authoring is gated). Under the operator's framing, mode 2 becomes the dominant discovery mechanism, with mode 1 as a complement for what no current goal touches.

**The substrate's learned topology converges toward what it's actually been asked to do, not toward an abstract coverage notion.** This is the right asymmetry for a substrate whose purpose is "reduce ambiguity across all horizons across actual usage."

### The validation-paired-with-capability accumulates a self-verification graph

Beyond the activity graph (templates connected by shape compatibility), the substrate accumulates a **verification graph** — for each capability X, the validator V_X that attests X works. The verification graph parallels the composition graph:
- Composition edge: "activity A's output shape Y feeds activity B's input shape Y"
- Verification edge: "activity A claims output shape Y; validator V_A agrees that A's output actually conforms to Y"

The substrate's confidence in composition correctness is the product of per-edge verification rates. **High-confidence compositions = high-coverage verification edges across the chain.** This gives the substrate a way to answer "how sure am I that this composition works" with measurable evidence, not just Thompson α/β.

## Part 4 — What's missing for this to work end-to-end

In priority order (the load-bearing prerequisites):

1. **Improvise + ribosome-extract for improvisation traces** (per prior turn). The substrate-side capability authoring loop where LLM-in-loop drives resolvers and ribosome extracts the template from the trace. Doesn't exist as a registered template today.

2. **Authoring proposals from LLM output** — when the LLM identifies it needs a missing capability, it emits an `authoring_proposals` block; downstream dispatch routes to make-activity / forge-vessel-for-shape / add-resolver-to-vessel as appropriate. Requires structured-output constraint on the LLM resolver.

3. **Validator-companion authoring** — when `make-activity` or ribosome produces a template, it ALSO produces a paired validator. Requires extending `make-activity.json` and `ribosome-extract.json` to author the companion. The validator-dispatch infrastructure exists; the pairing doesn't.

4. **iter-037's signature wire-bridge fix** (~10-20 LOC per iter-037). Once `context_thompson_scores` populates, the substrate can stratify "which authored capability worked under which signature." Without it, all the authored capabilities' learning rolls up to uniform posteriors.

5. **The forward arm's universal write** (Finding 8 #2). Every successful task should credit relevance of consumed impulses. Without this, the substrate can't learn which impulses helped which activities — disambiguation stays first-match.

6. **`forge-vessel-for-shape` made to work** (currently 1/12 success per iter-034). The primitive-shape gap-closer needs a working implementation.

7. **Audit↔state divergence fixed** (Finding 9). If the autonomous-promoter promotes silently while state stays `proposed=true`, no amount of authoring helps — the substrate can't actually use what it authored.

## Part 5 — Implications for the audit role

Under this framing the audit's job is:

1. **Watch what the substrate authors.** Templates landing as `proposed=true`, what their shape contracts claim, what they actually produce when first run.
2. **Watch what gets validated.** Validator-companion authoring rate. When V_X agrees with X's outputs, when V_X disagrees.
3. **Watch composition growth.** New two-hop chains forming, topology holes filling, orphan-producers gaining consumers.
4. **Watch state vs audit-trail.** Per Finding 9 — when the substrate logs that something happened, did it actually happen.
5. **File findings ONLY when authored outputs don't compose / claim more than they deliver / silently fail.** Don't gate authoring; observe it.

This is the audit posture the operator has been pushing toward across recent turns: **operational observation of the substrate doing its work**, not infrastructure design from outside.
