## 3. F-119 Escalated: coverage_progress is Structurally Always True

In investigation-046, F-119 was filed as "consecutive_progressing_cycles counter misleading." After examining the resolver source code, the issue is deeper.

The coverage-tick resolver builds `cells_over_time` as:
```typescript
for (let i = 1; i <= numWindows; i++) {
  const since = new Date(now - i * windowSize * 1000).toISOString();
  cells_over_time.push(await computeCountsForWindow(since, auth, allTemplates));
}
```

Each `computeCountsForWindow(since)` queries: "how many unique output shapes appear in all traces with `executed_at >= since`." With `since = now - i*3600s`:
- cells[0] = traces from last 1h to now
- cells[1] = traces from last 2h to now (includes all of cells[0]'s traces PLUS any from the prior hour)
- cells[2] = traces from last 3h to now
- cells[3] = traces from last 4h to now

**These windows are cumulative, not independent.** cells[3] is a superset of cells[2], which is a superset of cells[1], which is a superset of cells[0]. Therefore `cells[i].reachable_learned >= cells[i-1].reachable_learned` for all i is guaranteed by construction, as long as at least one trace exists in any window.

The monotonic check (`if (curr.reachable_learned <= prev.reachable_learned) reachable_learned_strictly_increasing = false;`) can ONLY return false if there are zero traces in a longer window — impossible when there are traces in a shorter window.

**coverage_progress=true is structurally guaranteed** whenever any shapes are learned. This makes it useless as a lift criterion gate. The S.4a criterion which depends on it is unresponsive to actual temporal coverage improvement.

**F-123 (NEW, HIGH):** The metric-reality inversion is directly observable this window. coverage_progress=true, yet:
- 1h-window learned: 8 (inv-046 at 02:58Z) → 5 (inv-047 at 05:21Z), **declined by 3**
- 4h-window learned: 15 → 12, **declined by 3**

The metric says "progressing." Every absolute value is lower.
