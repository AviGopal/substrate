## What's actually true (the findings that survive grounded verification)

### 1. Split-write architecture is real, but internally consistent

Per subagent #17's code-walk:
- α is written by `applyOutcomeToPosteriors` (`lib/posterior-update.ts:444-462`) to `variant_performance_metrics.thompson_alpha`, atomic `+= 1` on success.
- α is ALSO incremented by `propagateCreditAlongChain` (`:324-410`) — chain-credit propagates `γ^depth` α-deltas to ancestors of successful descendants.
- `successful_executions` on `variant_performance_metrics` is written by `POST /v2/activities/feedback` (`activities.ts:2290`); is NOT written by `POST /v2/activities/execution-traces`. The trace POST writes `successful_executions` to `activity_template` (different table).

The split is intentional (the `/feedback` path is documented as the canonical posterior-update entry); the audit's confusion was reading the variant_performance_metrics row without realizing the success counter for direct executions lands on the feedback path too. In current data, the feedback writes ARE happening (ok=750 attests).

### 2. `success_rate` field IS misleading

The `create-shape-provider-goal` row reports `success_rate = 0.0` despite `successful_executions / total_executions = 750 / 827 = 0.907`. This is a real defect — either the success_rate is stale (not recomputed on write) or it's been wired to a different counter. **Severity: substantive**, but not the kind of substrate-wide measurement corruption iter-034 alleged. This is a single-field staleness issue affecting one read surface.

To verify: a subsequent UPDATE to this row should recompute success_rate from ok/total. If the field stays 0.0 after a fresh execution, the recompute is wired wrong.

### 3. `impulse_relevance_metrics` IS empty (forward arm)

Confirmed: 0 rows. Per subagent #17's grounding, `learning-signal-writer` (`ias-executor-ts/src/resolvers/learning-signal-writer.ts:113-136`) writes to `/v2/activities/impulse-relevance` only when (a) `signal === "impulse_relevance"`, (b) `templateId` populated (F-39 fix), AND (c) `allImpulseIds.length > 0`. The resolver fires only when a template's task graph EXPLICITLY contains a `learning_signal_writer` task.

The three discovery probes (`create-shape-provider-goal`, `probe-reachable-unlearned`, `probe-untraversed-edge`) likely don't include this task in their declarations. **F-39 fixed the templateId-on-payload path; it did NOT wire the task into discovery-probe templates.** The forward arm is structurally inactive for the templates the audit was looking at because the resolver call is never dispatched in those execution paths.

**Severity: substantive**, not the alarmist "forward arm broken everywhere" iter-034 implied. Forward arm works for templates that include the task; doesn't fire for templates that don't.

### 4. `context_thompson_scores` IS empty (stratified Thompson)

Confirmed: 0 rows. The write path (`posterior-update.ts:487-533`) is gated by `trace.signature && typeof trace.signature_version === 'number'`. If traces arrive without `signature` populated, no write happens. Per subagent #17, the wire-payload-to-interface key bridge between `body.metadata.state_space_signature` and `TraceForPosterior.signature` was not visible in the grep — suggesting the field isn't being hoisted in the trace POST handler.

This is the only finding from iter-034 that survives at HIGH severity: **the substrate's signature-keyed conditional Thompson stratification is structurally not happening, even though all the schema and write code exists.** Either minibob isn't shipping `state_space_signature` in trace metadata, or the activity-api isn't reading it, or the field name mismatches. Per iter-027's grounding ("ISS is computed minibob-side ... activity-api re-derives server-side when absent"), this could be either the source side or the server side.

### 5. Templates running 0% success aren't growing α from nothing

For the `create-shape-provider-goal` row that DOES show 0 success in iter-034's snapshot, the explanation is now: at the moment of iter-034's snapshot, the feedback path had not yet credited any of the (then) 823 executions as successful. Between iter-034 (~23:30Z) and now (~00:15Z), the same template went from ok=0 to ok=750. That's 750 success-credits in 45 minutes — implausible from execution alone (the boredom timer is 30 min), so the credits are likely catch-up updates from the feedback path processing a backlog.

**This itself is a finding**: the feedback path's `successful_executions` write lags execution writes by enough time to make snapshots look pathological in the interval. Severity: substantive — read consistency on success_rate / successful_executions / total_executions across a single row is not guaranteed mid-cycle.
