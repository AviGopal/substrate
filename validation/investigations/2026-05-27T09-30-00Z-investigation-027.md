## 1. The trace → concept-db learning loop (the actual chain)

`task.completed` fires on activity-api's WS broadcaster carrying `data.input_impulse_ids` / `data.output_impulse_ids` / `data.impulse_resolutions`. concept-db's `ExecutionObserver` (`repos/concept-db/src/services/execution-observer.ts:288-316`) subscribes with authenticate+catchup. `handleTaskCompleted` (`:383`) calls `buildUsageRequestsFromTaskCompleted` (`:146`) → `extractConceptRefs` (`:100-140`) filters for `shape === 'concept'` or `concept_id` set or id-prefix `concept:` / `concept_`. Each match → `recordUsage` (`repos/concept-db/src/resolvers/usage.ts:17`):

1. Creates `concept_usage` row with `outcome=success|failure`, `trace_id=execution_id`, `task_id` (`:25-48`).
2. Runs Bayesian update on `times_succeeded`/`times_failed`/`relevance` (`updateConceptMetrics`, `:75-105`).
3. **Forwards** to activity-api `POST /v2/activities/impulse-relevance` with `impulse_id=concept:<id>`, `source=concept-db` (`:110-145`) — drives Thompson β/α on activity-api's `impulse_relevance_metrics`.

So **three rows are written per concept-shape impulse in one trace**: activity-api `impulse_resolutions[]` entry inside the trace, concept-db `concept_usage`, activity-api `impulse_relevance_metrics`.

## 2. The seam between concept-db and activity-api traces

The join key is `trace_id = execution_id` — but it's a free-form string in concept-db (`usage.ts:39`), not a foreign key into activity-api's trace table. **Correlation exists by convention; not enforced by either DB.** Same SurrealDB instance, `namespace=activity-system, database=learning_loop`.

**Canonical reader of the pair**: nobody currently. Workbench renders trace `impulse_resolutions[]` (ExecutionHistoryPanel, ShapeProvenanceTree) but doesn't pivot into concept-db. Concept-db's upkeep activities consume `concept_usage` aggregates alone — they don't read back trace rows. **The trace-to-concept correlation is observation-only. No closer of the loop.**

## 3. How the substrate learns to do things — and the gating that matters

Five LIVE learning surfaces:

- Template Thompson α/β in `variant_performance_metrics` + conditional `context_thompson_scores` keyed on `(template_id, state_space_signature)` (`repos/metabob-activity-api/src/lib/posterior-update.ts:220-286`)
- Concept usage in concept-db (§1)
- Composition success with ancestor chain credit via `propagateCreditAlongChain` (`posterior-update.ts:308,369`)
- Validator α/β written by `validator-dispatch.write_learning_signals` → `learning-signal-writer.ts:1-40`
- Impulse relevance (`impulse_relevance_metrics`)

**But generating new templates has two paths, both gated off by default:**

- `ribosome-extract.json:31` — `dispatch_write` task gated on `applyExtraction` (default **false**). Today emits an `extractedTemplate` *proposal impulse*; does **not** persist a template.
- `make-activity.json:39` (at `repos/deployment/vessels/minibob/src/embedded-templates/`) — six-task meta-activity; `extract_template` task gated on `applyTemplateExtraction` (default **false**). Same proposal-only behavior.

**The substantive finding:** today the substrate **optimizes ranking of existing templates** (Thompson) and **proposes new ones** (ribosome, make-activity) — but the write step is gated off. The "learns how to do things" loop is observation-complete and proposal-complete; the actualization step is operator-gated by default.

## 7. ISS and PSS

**ISS = Impulse State Signature** (canonical name: `state_space_signature`). Defined at `openspec/changes/2026-05-17-state-space-signature-thompson-keying/specs/state-space-signature/spec.md:13`. Format: lowercase-hex prefix of 16 chars (64 bits) of `sha256(canonical-encoding(input))`. Input: `(signature_version, sorted shape multiset, sorted (shape, producedBy?) tuples, sorted missing-shape set)`.

Computed minibob-side in `buildExecutionTraceWirePayload` (attaches as `payload.metadata.state_space_signature`, `signature_version=1`); activity-api re-derives server-side when absent.

**Keyed on**: `context_thompson_scores` rows `(org_id, template_id, signature, signature_version)`. The recommend path looks up `(template_id, signature)` first; falls back to template-level `variant_performance_metrics` when `n_observations < SIGNATURE_SAMPLING_FLOOR` (default 5).

**What it enables**: "template X under state signature S₁ has α=15, β=0; under S₂ has α=0, β=3" — distinguishes behavior from aggregate identity. This is the real machinery behind conditional Thompson recommendation.

**PSS**: searched `PSS`, `pool_state_space`, found no separate definition. `pointer_state_space` and `impulse_state_space` exist at `activities.ts:5040` paired together — both Phase 11 surfaces. **PSS as a distinct construct does not exist in code today.** It's likely a conflation in audit/validator framing — the "pool" axis is one of ISS's inputs (the sorted shape multiset), not a separate signature.

## Substantive corrections to prior audit framings

### Correction A: iter-022's `llm-prompt.ts:85` retrieval point is **not a real read path today**

My iter-022 design and iter-025 envelope assumed concept-db retrieval happens at `llm-prompt.ts:85` pre-interpolation. **The subagent could not confirm any concept-db-aware read in `repos/ias-executor-ts/src/resolvers/llm-prompt.ts`** — concept retrieval today appears to be operator/template-explicit (a template that uses a `concept`-shape pointer impulse). The Cα/Cβ "autonomous injection at every LLM call" is aspirational. **The envelope design from iter-025 needs to grapple with this**: deploying the envelope does not magically activate concept-db retrieval. A separate code change is needed at the resolver level.

### Correction B: capability-generation is gated off by default

Even if concept-db were full, even if the envelope shipped, the substrate still **cannot autonomously register new templates from learning**. Both `ribosome-extract` and `make-activity` default to `applyExtraction=false` / `applyTemplateExtraction=false`. The proposal impulses accumulate but no template is persisted unless an operator (or a chain that flips the flag) enables the write. This re-frames what "S2 lift" means structurally: lift is operator-endorsement-of-proposals, not autonomous-template-authoring.

### Correction C: "PSS" was my (and likely the validator's) conflation

I used ISS/PSS terminology assuming two distinct constructs. There is only one — the state_space_signature (ISS). The "pool" axis is one of its inputs, not a separate signature. Future audit cycles should drop "PSS" terminology.

### Correction D: Non-LLM resolvers do not have a learning loop today

I have been writing as if iter-022's Cβ (resolver_pattern concept type) was a near-term wire-up. It's aspirational with **zero code hits**. Pattern resolvers like `impulse_pool_selection` are static heuristics. Thompson keys on `(template, signature)`, not `(resolver_id, shape_pair)`. Cβ remains a worthwhile design but its implementation surface is larger than iter-022 implied — it needs a new posterior-update path AND a new write resolver.

## Closing — what concept-db IS today

> A SurrealDB-backed vessel that stores concept rows (impulse-shaped data with content, edges, usage counters), exposes them via MCP tools and HTTP, and passively maintains a relevance score per concept by subscribing to activity-api's WebSocket stream and counting which concepts appeared in successful vs failed traces. It forwards the same signal back to activity-api as `impulse:concept:<id>` for cross-vessel posterior tracking. Its upkeep scheduler periodically mutates the graph using those counters. It is wired to *receive* signals from every vessel that emits concept-shape impulses, but **no other vessel reads from concept-db autonomously today** — concept retrieval happens only when a template explicitly references a `concept` pointer. **It is a learning sink with a publish surface, not yet a learning loop closed at the read side.**

## What this means for the design arc 022→026

The iter-022→026 design arc presupposed three things that turn out to be more aspirational than I assumed:

The envelope design (iter-025) is still right *structurally* but its deployment value depends on prerequisites that don't exist. The cheap measurements remain cheap (gap.classified emission, confabulation-rate logging, cold-start probe) — those are pure observation. But the *substantive* changes (envelope rendering, concept conditioning) need accompanying code at the read-path.
