## A. Safely enabling capability generation

**The flag is one bit.** `applyExtraction` (`ribosome-extract.json:30`) and `applyTemplateExtraction` (`make-activity.json:39`) both default `false`. Flipping routes the synthesized `extractedTemplate` impulse to `activityTemplate_write` via `impulse-resolve` (`ribosome-extract.json:156-163`, `make-activity.json:238`).

**The existing promotion bar.** Ribosome enforces six structural rules before write attempt (`ribosome-extract.json:130-143`): id regex, every task has prompt-or-resolver, resolver in known set, tag regex, non-empty inputShapes/outputShapes per task, `metadata.author === 'ribosome-pattern'` (recursion guard). Quality gate: `qualityThreshold=0.7` default, decided by LLM `assess_quality` against a rubric. **Hard gates: recursion-safety + status===completed; everything else is LLM-judged heuristic.** The `template_quality_scorer` and `template_compliance_validator` *deterministic* resolvers named in `metadata.openQuestions` (`:260, :268`) **do not exist today**.

**Write target is the live registry.** No `proposed_activity_template` table. With `applyExtraction=false`, the extractedTemplate impulse lives only in the trace's impulse pool. No review queue, no operator surface, no TTL. Workbench-side `ExtractedTemplate` review surface is aspirational — not in the workbench page list per CLAUDE.md.

**Cascade risk.** Recursion gate is string-match on `metadata.author` (`ribosome-extract.json:69, 84-rubric-rule-1`). If LLM synthesis drifts, no deterministic second guard. The ~800 doubled-prefix wrap rows per CLAUDE.md are a sample of what this bug class produces in registry data.

**Observability dependence.** Findings 3/4/5 (`openspec/changes/2026-05-23-substrate-explicit-vessels/findings/audit.md`) — lifecycle channels emit without subscribers — directly compound: capability generation writing to registry without observable lifecycle is the worst case. Floods discovered post-hoc by registry size, not trace inspection.

**Smallest concrete change.** Add `proposed=true` boolean to `activityTemplate_write` payloads when `applyExtraction=true` (one boolean in pointer config at `ribosome-extract.json:160-163` and `make-activity.json:238`). Activity-api treats `proposed=true` as registry-visible but **selection-invisible** (Thompson recommender skips). Operator promotes via separate `activityTemplate_promote` write. Preserves one-bit flip + provides rollback. No new shapes — existing-field discipline.

## B. Mixed-tier composition — choice, learning, navigation

**Engine is tier-agnostic.** `engine.ts:159` dispatches by resolver id. `taskRecords.resolverTier` (`engine.ts:248`) is *recorded* from `runtime.resolvers.get(task.resolver)?.tier` but never branches behavior. Mixed-tier templates execute identically to single-tier.

**Concrete distribution from real templates:**
- `repos/ias-executor-ts/src/templates/lifecycle/audit-test-report.json`: 5 tasks, 3 deterministic (`impulse-resolve`), 1 pattern (`validation`), 1 llm (`audit-test-report.json:57,79,104,130,163,186`)
- `ribosome-extract.json`: 7 tasks, 4 llm-prompt, 3 impulse-resolve

**The ratio is shape-driven, not philosophy-driven.** Deterministic resolvers appear where I/O is structured (fetching trace signatures, persisting templates, validating). LLM resolvers appear where I/O is ambiguous (quality scoring, template synthesis, compliance review).

**Autonomous-synthesis bias.** `make-activity.json:215-246` synthesizes via LLM with no heuristic biasing resolver-tier. Ribosome preserves the source trace's resolver ids (`:109` rule 7). `make-activity` LLM picks freely; **default bias is LLM-heavy** because the prompt doesn't enumerate deterministic resolvers as preferred.

**Variant boundary is the unit of learning.** Thompson α/β keyed at variant; variant-of-variant rewriting (changing task-2 from bash to llm) requires new variant id, new α/β. Confirmed by ribosome metadata extracting new template (new id) per qualified trace, not mutating existing. **There is no `(resolver_id, shape_pair) → success_rate` table at runtime** — Cβ's `resolver_pattern` primitive (iter-022) confirmed aspirational.

**Per-task config heterogeneity.** `ontology.ts:46-47`: `inputShapes?: (string | InputShapeRef)[]`. `InputShapeRef` (`:29-36`) has `shape`, `cardinality: "any" | "all" | "exactly_one"`, `producedBy` predicate. `task.config` and `task.retry` opaque to engine, passed via `ResolverContext` (`engine.ts:176-190`); retry parsed at `engine.ts:194-200`. **No schema enforces config-shape against resolver-tier** — each resolver validates its own.

**Smallest concrete change.** Add concept write at `engine.ts:248` recording `(template.id, task.id, task.resolver, inputShapeNames, outputShapes, success)` per task record. This is the `resolver_pattern` primitive iter-022 named — *observable* today via trace tasks but *not aggregated*. With per-task aggregation, ribosome's `synthesize_template` prompt (`:109`) can read which resolver tier has highest success rate for `(input_shape, output_shape)` and bias synthesis. No new shapes, no engine changes — trace-side aggregation resolver only.

## C. Impulses as variables, lazy population — the actual mechanism

**Declaration.** `ontology.ts:46-47` declares task `inputShapes`/`outputShapes`. Optionally `InputShapeRef` with `cardinality` and `producedBy` predicate.

**Slot-binding fires events but does NOT block.** `engine.ts:84-125`: before each task with declared inputShapes, executor scans `runtime.store.all()`, computes `missingShapes`, emits `lifecycle:task:preBinding` AND `lifecycle:gap:classified` (when missing > 0). **Then proceeds immediately to `task.started` and `resolveInputs` at `:127, :134`.** `resolveInputs` (`:450-478`) hard-throws if no candidate exists (`:465-467`).

**Gap-filling is side-band.** Lifecycle subscribers (`slot-binding.json`, `validator-dispatch.json`) must populate the store via their own `lifecycle:task:preBinding` subscription **BEFORE** the executor reaches `resolveInputs`. The `await this.emit` (`engine.ts:95`) returns when the event sink's synchronous dispatch returns, but lifecycle-subscribed activities run **as separate executions** — there is no join. **In practice this works because dispatch happens to be synchronous enough; the design is fragile.**

**Interpolation.** Two interpolators. Engine-wide: **none** (the engine does not interpolate `task.config`). Resolver-side at `llm-prompt.ts:47-67`: regex `/\{\{([\w]+(?:\.[\w]+)*)\}\}/g`, walks dotted paths against `variables`, falls back to literal. At `:89-96`, declared inputShapes are merged into variable namespace by shape name — `{{shape_x}}` resolves to loaded content of first inputImpulse with `metadata.shape === "shape_x"`. Reused by `resolvers/iteration.ts:32`.

**No lazy load.** Impulses stored as full objects with `loaded`/`content` fields (`impulses.ts:32-43`). Executor `store.put`s seeded at `engine.ts:48-50`; resolver outputs at `:228-232`. `resolveInputs` returns full Impulse objects already in store. **There is no on-demand fetch triggered by a placeholder hitting an unloaded impulse** — placeholder either finds loaded content or interpolates to literal `{{...}}` (`llm-prompt.ts:55`). The CLAUDE.md "lazy loading" claim describes the impulse *pointer* model (memo/file/directoryTree) but the engine itself eagerly materializes. **Aspirational on the engine side.**

**Escalation via subgoal, not pull.** `engine.ts:110-124` emits `lifecycle:gap:classified`. `slot-binding.json:243` → `escalate_unbindable` → dispatches `create-shape-provider-goal` via `activity` resolver. **This is a new goal execution, not an in-band pull.** The parent task's `resolveInputs` will still throw if the subgoal hasn't completed before executor reaches it. Recursion guard: `parent_depth` vs `max_recursion_depth=3` (`slot-binding.json:218`).

**Smallest concrete change.** At `engine.ts:134`, before `resolveInputs`, await in-flight `lifecycle:task:preBinding` subscriber chains and re-scan the store. Add a `runtime.eventSink.flush(executionId, taskId)` primitive on `LifecycleEvent` of type `task:preBinding` that blocks until all subscriber chains for that taskId have completed, then re-scan. **Converts "side-band hope" into "explicit pull"**. Insertion point: `engine.ts:126`.

## Staging recommendation: ship C first

**C is the right one to enable first.** Reasoning:

- **A and B both write to the registry.** Both depend on observability infrastructure (Findings 3/4/5 lifecycle channels) that does not exist. A flood in either has long blast-radius.
- **B's smallest change** (aggregated `resolver_pattern` writes) is itself blocked on observability — without it the aggregation reads from incomplete traces.
- **C, by contrast, fixes a *structural* fragility in the existing execution path.** Today gap-filling depends on synchronous-enough event dispatch; `resolveInputs` hard-throws on shapes that a lifecycle subscriber *would have* provided.
- **Closing the join at `engine.ts:126`** turns the lifecycle-subscriber pattern (slot-binding, validator-dispatch, ribosome-extract) from "hope it ran in time" into "we waited for it" — making A and B *safer* to enable later because the gap-fill primitive they both depend on becomes deterministic.
- **Risk is low**: one new sink primitive, one await. **Reach is high**: every template with declared inputShapes benefits.
- **It unblocks the operator's framing** ("populate what is needed, when it is needed") by giving the engine a place to *pull* impulses rather than hoping they're *pushed*.

## Implications for the design arc 022→027

This re-orders the prior arc:

1. **First**: ship C — `eventSink.flush()` primitive + await at `engine.ts:126`. Makes lifecycle-subscriber gap-filling deterministic. **Prerequisite for everything else.**
