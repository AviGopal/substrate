# Investigation 024 — The LLM resolver inside an activity: brutally minimal context, no envelope, synthesis-failure confabulates

Subagent #6 (transcript: `/tmp/.../a6517ddc487788caf.output`) ground-truthed what the LLM actually sees at the wire when fired from inside an activity. The result is more constrained than I expected and has direct consequences for the gap-detection framework in investigation-023.

## What the LLM literally sees

The assembly path is ruthlessly minimal. At `repos/ias-executor-ts/src/resolvers/llm-prompt.ts:78-89`, the resolver reads **exactly two fields** from the `ResolverContext`: `context.task.prompt.template` and `context.variables`. It runs `{{placeholder}}` interpolation and hands the result to `LLMPort.generate({prompt, systemPrompt})`. Everything else in `ResolverContext` is dropped before the wire call.

The wire-format is even thinner. `HttpLLMPort.generate` (`hosts/goal-host.ts:299-340`) POSTs `{type:"llm_completion", prompt, model, max_tokens, system?}` to `llm-resolver-vessel:8220/resolve`, which constructs an Anthropic Messages call with `messages: [{role:"user", content: body.prompt}]`. **No system prompt unless `task.prompt.systemPrompt` is set** (survey: no canonical template sets it). No tools. No message history. The `metadata` field on `LLMPort.generate` (`ports.ts:71`) **exists but is unused** by every caller — the natural slot for `goal_class`, `gap_type`, `composition_depth`, `variant_id`, `thompson_alpha/beta` is sitting empty.

### Worked example — `compose_goal` task #8 of `create-shape-provider-goal`

Template at `create-shape-provider-goal.json:233`, ~3000 tokens. Composition: one-paragraph framing ("you are composing a shape-provider goal"); seven labeled signal slots (`{{impulse:forward_chain_producers_result}}` etc.); six parameters (`{{target_shape}}`, `{{parent_goal_text}}`, `{{available_shapes}}`, `{{parent_depth}}`, `{{max_recursion_depth}}`, `{{remaining_budget_usd}}`, `{{parent_execution_id}}`); three guard-logic specifications (depth/cycle/budget in prose); strict-JSON output spec. Post-interpolation, the LLM sees a single concatenated user-role string of ~1500–2500 tokens. **Ratio of parent-supplied signal to task-instruction prose is roughly 1:2 — the prompt is mostly its own scaffolding.**

### What's NOT in the LLM's window today

1. **Originating goal text.** `options.goalContext.goal` exists at `engine.ts:107,326` and is emitted on `lifecycle:task:preBinding` events, but is never threaded into `variables` for `llm-prompt`. Templates have to manually re-pipe goal text via a variable (compose_goal does this; every other LLM template would have to opt in identically).
2. **`compositionChain`.** Present on `ResolverContext`, used by the engine for cycle guards, not passed. Compose_goal's prompt asks the LLM to honor cycle guards but provides only the immediate parent's trace via `parent_chain_lookup` — not the full ancestor chain.
3. **Thompson posteriors** on the variant being executed.
4. **The gap-type classification** from the executor side (investigation-023's seven types) — invisible to the LLM.
5. **Sibling-task outputs** not declared in `inputImpulses`. The engine intentionally narrows the pool at `resolveInputs` (`engine.ts:119`).
6. **Prior turn output.** Every dispatch is single-shot; no conversation context.
7. **Failure history** of this template/variant. Even per-task retry state is opaque.

**Operational implication of Section A:** the LLM's behavior in this substrate is, by construction, *fully determined by the template author's interpolation choices*. There is no ambient context, no system prompt, no implicit composition_chain, no `goal_class` envelope. A template that forgets to pipe `parent_goal_text` produces an LLM that has no idea what the user wanted. This pushes ALL conditioning responsibility onto template-time prompt-writing — **the LLM cannot tell on its own whether it is in a top-level user goal, a boredom-fired probe, or a recursive `compose_goal` cascade.** It only knows what the literal prompt string told it.

## Five goal-classes, one wire format, zero discriminator

| # | Goal-class | Wire path | LLM-visible discriminator |
|---|------------|-----------|--------------------------|
| 1 | Top-level user goal | `/run-goal {goal,variables}` | only if template pipes `{{goal}}` |
| 2 | Boredom-fired meta-goal | same `/run-goal` | none beyond the canned goal text |
| 3 | Composed sub-goal (cascade) | downstream dispatch | only inferable from prompt framing |
| 4 | Lifecycle-routed (slot-binding, validator-dispatch inner LLM) | same `llm-prompt` resolver | none — structured output demanded, but no signal that it's a binding/validation prompt |
| 5 | Self-reflective (ribosome, concept extraction) | same | same |

The LLM cannot distinguish these except by reading the prompt's natural-language framing. No envelope field, no system prompt, no metadata channel populated.

## Can the LLM participate in gap detection?

This is the load-bearing piece. The executor-side classifier from investigation-023 covers 6 of 7 gap types deterministically; **gap type 6 — `synthesis-failure` — lives only inside the LLM's head.**

Three concrete LLM-resolver behaviors today:

- **Insufficient-input recognition: NONE.** If forward_chain_producers, prior_paths, cooccurrence, concept_lookup all return empty, the prompt instructs the LLM to "handle defensively." The LLM has no `unable_to_synthesize` output discriminant — its only channel is the strict-JSON goal-shape. **The LLM WILL confabulate.** The substrate dispatches the confabulated goal. Downstream activity likely fails. The failure is attributed to whatever child gets selected — NOT to the synthesis step.
- **Prompt-routing-mistake detection: IMPOSSIBLE.** If a `compose_goal` template were invoked for a context that needs `validation_result`, the LLM would emit goal-shape JSON because that's what the prompt demands. It has no view of context apart from the prompt.
- **Self-aware-refusal capacity: ZERO.** The architecture doesn't even support blind-attempt-and-fail; the LLM cannot signal failure through the `llmText` impulse channel because consumers expect parseable JSON and treat parse-failure as `verifier_negative` (the validator's α/β, not the synthesis's). **The substrate is blind to synthesis-failure as a distinct mode today.**

**This is corruption of binding-layer Thompson posteriors at the rate of LLM confabulation over empty signal sets.** Every "successful" compose_goal that produced a bad downstream cascade increments α on the synthesis template even though the synthesis itself was the failure point. Same corruption pattern H1 (two-sided-trace finding) flagged for cross-vessel traces — here, intra-vessel, between executor and resolver.

The ratio of **(signal-empty AND confident-output AND downstream-fail) / (signal-empty AND any-output)** is the **confabulation-into-failure rate** — a direct measurement of how blind the substrate is to synthesis-failure.

## Operational implications, in priority order

1. **The `metadata` channel on `LLMPort.generate` is the load-bearing unused field.** Populating it with `{goal_class, gap_type, composition_depth, variant_id, thompson_alpha, thompson_beta, parent_goal}` and rendering it as a system prompt or prompt-prefix would give the LLM the conditioning surface it currently lacks. ~30 LOC change to the `HttpLLMPort.generate` path and one consumer-side prompt-template convention.
2. **The LLM has no failure channel.** Any synthesis-failure becomes either a parse error (attributed to the wrong layer) or a confabulated success (attributed to a downstream failure of the wrong template). Until the trace sink accepts an `unable_to_synthesize` discriminant, the substrate's posterior corruption is structural.
3. **Concept-db injection (Cα, iter-022) lands exactly here.** The interpolation site at `llm-prompt.ts:85` is where `{{prompt_directives}}` would slot in. If concept-db retrieval is wired pre-interpolation, every directive the substrate has learned conditions every LLM call — without prompt-author opt-in.
4. **All five goal-classes flow through the same wire format.** A simple `goal_class` field in `metadata` plus a one-line system-prompt prefix ("you are operating in goal_class=COMPOSED_SUB_GOAL at depth=2 with gap_type=missing-shape-in-pool") closes the largest provenance gap with minimal infrastructure.
