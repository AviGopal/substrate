## What the chunk says about the class (memory-recall)

- **The recurring reason is the storage primitive, not any one mechanism.** Every kept mechanism here (retire, mirror, expectation-scan, battery writes) calls one resolver whose load swallows errors to `[]` and whose saves share a fixed tmp path, with an env-derived path and newest-N recall. Three fixes (the 09-22 merge, the 09-23 retire, and the mirror of 169 notes on 06-15) were each undone by the next event. Until that primitive gets durability (a fail-closed read, a unique tmp, an append log) and a location that is one shape across nodes rather than one file per node, "keep" on everything above only means "keep writing into a store that can empty itself".
- **Node-local memory is not absence, but it is unreachable today.** Node 2's development-vessel serves `memoryNote` from its own 1 KB store. A recall on node 2 never reaches node 1's 59 notes or the 1,184 archived ones. The p2p principle says memory recall should resolve through discovery to wherever the notes live, so row 6's concept-db import is the cheapest way to make the fossils reachable everywhere.
- **What worked, and should be reused rather than re-minted:** failure memory (row 3) is the only mechanism in the chunk that demonstrably stops a repeat for the same reason. Any new "remember past failures for the drafter/gap lane" proposal should extend it, not mint a sibling.
