# Learning audit, round 2 — after the tier 0-4 fixes

## Verdict in one paragraph

The tier 0-4 fixes are real, correct, and mostly landed. On this substrate they are mostly not running. The vessel that emits the traces the learning loop grades — `goal-host-vessel` on `substrate-live` — is serving commit `5be4cfa`, loaded at `2026-08-19 01:54:10 UTC`, while the fixed file sits on disk since `2026-08-20 01:13:54 UTC`. Bun does not hot-reload, `NRestarts=0`, `ActiveState=active`, `/health` 200 — every signal green. Worse than a transient: pull-sync writes its content marker (`substrate-pull-sync.sh:1040`) *before* the restart block (~`:1204`), so the next tick short-circuits at `:519` and the documented `RESTART_DEFER_MAX` bound is unreachable; the deferral counter is frozen at `1` of `3` and three later ticks (01:25, 01:34, 01:44) say nothing about goal-host. The log's own promise — "mirrored source takes effect on the next tick" — is false. This is not "credit is blocked": credit demonstrably flows on the hub side, chain credit resolves, the six added `alphaBetaDelta` sites were already *applying* their grades and only discarding the return value. The honest headline is narrower and more annoying: **the fixes are code the trace-emitting vessel is not running, and the mechanism that should have loaded them is unbounded.** Separately, one defect not in any tier is doing more live damage than anything the tiers addressed — `success_rate` is exactly binary across all 1516 metrics rows, and the substrate's own goal generator is minting `critical`-priority goals asserting "0% success rate" about arms running at 98%.

But `learning_liveness` observations fleet-wide: **zero**. `learning-liveness-probe.timer` landed at 01:25:27 via pull-sync onto a container that booted `2026-08-18T07:11:51Z`, and the only code that enables a never-enabled unit is `apply-inventory.sh:161-168`, invoked solely from `entrypoint.sh:24-28`. Nothing in the system can observe that the arm is held, so nothing will ever propose lifting it.

## What is still preventing growth

A comment naming the wrong writer is how this claim survived several audits.
- **`THOMPSON_DECAY_HALFLIFE_DAYS` "inert on the coalescing path"** — refuted. `resolveThompsonDecayHalfLifeDays()` has three readers, and the dominant one is `activities.ts:6069` on the `/recommend` selection path, feeding read-time decay at `:6095/:6204/:6412-6420`. Authoring the row changes what the selector samples. Residual: the flush omits the 5th argument (`posterior-aggregator.ts:188`) so hot rows bake the hardcoded 3-day default while idle rows honour the shaped value — a real inconsistency, not an inert knob.
- **"Chain credit is written to a variant row that cannot exist"** — refuted. The lookup queries `v_paradigm_execution_traces`, which projects `meta::id(id) AS execution_id` (bare) in every current definition; the `execution:` prefix came from a *different* endpoint's projection. Both cited ancestor ids resolve live to real `variant_id`s.
- **`composition-graph.ts` amplifying the binary `success_rate`** — refuted. It reads `composition_node`, a different table maintained as a JS float mean, and has zero production importers. `health-scoring.ts` likewise computes its own rate in JS over its own table. The one live amplifier is `task-generator.ts`, which makes the finding narrower and worse.
- **"Ribosome-origin arms are systematically starved of credit"** — refuted. Origin is a proxy for cohort: `reach-classify.ts` lost its `legacy-success` fail-open on 2026-08-06 (`cfb455e`), whose top consumers were exactly the machinery ticks used as the control group. Those arms hold frozen pre-08-06 credit that current code could never grant and that decay never touches (decay is write-time only). No grading or selection path reads an id prefix. A control-class arm (`mitosis-tick`, mean 0.078) is below the learned-activity median.
- **"683 of 800 goal paths executed once ⇒ pathways are never re-walked"** — refuted by the system's own instrument. `path_signature` is keyed per goal-hash *and* per effect surface, so cross-goal reuse — the documented 78% case — lands in a *new* singleton row. `walk_tier` in those same rows shows 87 `learned_pathway` entries, 82 of them singletons. Singleton count measures goal-text repetition and key granularity, not reuse.
- **"`grep` proves nothing reads X"** — the operator-facing one. Five files under `repos/*/src` use literal NUL bytes as Map-key delimiters (`impulses.ts:5549,5563`; `cluster-posterior.ts:227`; `posterior-aggregator.ts:527,623`; `dead-end-decision-scan.ts:912`; `operator-review-patch.ts:1096`). GNU grep handles this loudly; this environment's `grep` is a shim to `ugrep -I`, which returns nothing and exit 1 — silently. ripgrep reports pre-NUL matches with a stderr warning and is silent only past the first NUL. `git grep` is immune. Two "grep-verified: no consumer" claims in commit messages rest on the shimmed tool; both happened to survive re-check with `-a`. Use `git grep`.
