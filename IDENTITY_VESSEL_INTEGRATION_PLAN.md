# Identity Vessel Integration Plan

## Goal

Ensure that API keys generated by identity-vessel can be used to authenticate with activity-api's `/v2/auth/apikey` endpoint, creating a unified API key system.

## Current State

### Identity Vessel (Key Generation)
```typescript
// repos/identity-vessel/src/services/keyGeneration.ts
// Generates HMAC-SHA256 signed keys
// Format: Base64(mb_live-<org_id>-<user_id>-<key_id>-<signature>)
generateApiKey(orgId, userId, options) {
  const keyId = `key_${generateRandomString()}`
  const signature = hmac(apiKeySecret, `${orgId}:${userId}:${keyId}`)
  const rawKey = `mb_live-${orgId}-${userId}-${keyId}-${signature}`
  return base64url.encode(rawKey)
}
```

**Validation:**
- HMAC signature verification (<10μs)
- Redis revocation check (~1ms)
- Total: <2ms

### Activity API (Current Authentication)
```typescript
// repos/metabob-activity-api/src/routes/auth.ts:151
// Uses SurrealDB RECORD access - DIFFERENT system!
auth.post('/apikey', async (c) => {
  const { api_key } = await c.req.json()

  // Authenticate via SurrealDB RECORD access
  const authResult = await db.signin({
    access: 'apikey_record',
    variables: { api_key }
  })

  // Returns JWT with org_id, user_id, scopes from SurrealDB
})
```

**Problem:**
- Identity-vessel keys use HMAC validation (no DB storage)
- Activity-api expects keys in SurrealDB with argon2 hashes
- These are **incompatible systems**

---

## Solution: Delegate Validation to Identity Vessel

### Architecture

```
Client (CLI/IDE)
    ↓ (sends API key)
activity-api (/v2/auth/apikey)
    ↓ (delegates validation)
identity-vessel (/v1/auth/resolve)
    ↓ (validates HMAC + checks revocation)
Returns auth context
    ↓
activity-api (returns JWT token)
```

### Benefits

1. **Single Source of Truth**: Identity-vessel is authoritative for API keys
2. **No Dual Storage**: Keys only exist as HMAC signatures, not in SurrealDB
3. **Fast Validation**: <2ms via identity-vessel HTTP call
4. **Unified Key Management**: Generate, revoke, rotate all in one place
5. **Backward Compatible**: Can support both methods during migration

## Implementation

### Step 1: Update Activity API Auth Route

Create new implementation that delegates to identity-vessel:

```typescript
// repos/metabob-activity-api/src/routes/auth.ts

// Add helper function to validate via identity-vessel
async function validateApiKeyViaIdentityVessel(apiKey: string): Promise<{
  authenticated: boolean
  orgId?: string
  userId?: string
  keyId?: string
  scopes?: string[]
  reason?: string
}> {
  const identityVesselUrl = process.env.IDENTITY_VESSEL_URL ||
    'http://identity-vessel.activity-system.svc.cluster.local:8080'

  try {
    const response = await fetch(`${identityVesselUrl}/v1/auth/resolve`, {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({
        impulse: {
          type: 'authentication',
          pointer: {
            type: 'apiKey',
            apiKey
          }
        }
      }),
      signal: AbortSignal.timeout(5000) // 5s timeout
    })

    if (!response.ok) {
      return {
        authenticated: false,
        reason: `Identity vessel returned ${response.status}`
      }
    }

    const result = await response.json() as {
      success: boolean
      data?: {
        authenticated: boolean
        orgId: string
        userId: string
        keyId: string
        scopes: string[]
      }
    }

    if (!result.success || !result.data?.authenticated) {
      return {
        authenticated: false,
        reason: result.data?.reason || 'Validation failed'
      }
    }

    return {
      authenticated: true,
      orgId: result.data.orgId,
      userId: result.data.userId,
      keyId: result.data.keyId,
      scopes: result.data.scopes
    }
  } catch (error) {
    console.error('[auth] Identity vessel validation error:', error)
    return {
      authenticated: false,
      reason: error instanceof Error ? error.message : 'Network error'
    }
  }
}

// Update /apikey endpoint
auth.post('/apikey', async (c) => {
  try {
    const { api_key } = await c.req.json()

    if (!api_key) {
      return c.json({
        error: 'invalid_request',
        message: 'api_key is required'
      }, 400)
    }

    // Try identity-vessel validation first (for new HMAC keys)
    const validation = await validateApiKeyViaIdentityVessel(api_key)

    if (validation.authenticated) {
      // Generate JWT token with validated auth context
      const db = await surrealDB.getInstance()

      // Create JWT token using SurrealDB's token generation
      // This ensures compatibility with existing JWT middleware
      const token = await db.signup({
        namespace: config.surrealdb.namespace,
        database: config.surrealdb.database,
        access: 'jwt_token', // Use a JWT-only access method
        variables: {
          org_id: `organizations:${validation.orgId}`,
          user_id: `users:${validation.userId}`,
          key_id: validation.keyId,
          scopes: validation.scopes || ['read', 'write']
        }
      })

      // Calculate expiry (15 minutes)
      const expiresIn = 900
      const expiresAt = new Date(Date.now() + expiresIn * 1000).toISOString()

      return c.json({
        token,
        expires_at: expiresAt,
        expires_in: expiresIn,
        org_id: validation.orgId,
        user_id: validation.userId,
        scopes: validation.scopes || [],
        source: 'identity-vessel' // Indicate which system validated
      })
    }

    // Fallback to SurrealDB validation (for legacy keys)
    // This maintains backward compatibility during migration
    console.log('[auth] Identity vessel validation failed, trying SurrealDB fallback')

    // [Keep existing SurrealDB validation code here for backward compatibility]
    const db = new Surreal()
    await db.connect(config.surrealdb.url)
    await db.use({
      namespace: config.surrealdb.namespace,
      database: config.surrealdb.database,
    })

    try {
      const authResult = await db.signin({
        access: 'apikey_record',
        variables: { api_key }
      })

      if (!authResult) {
        return c.json({
          error: 'invalid_api_key',
          message: 'API key is invalid, expired, or revoked'
        }, 401)
      }

      // [Existing JWT extraction and response logic]
      const jwtToken = typeof authResult === 'string'
        ? authResult
        : (authResult as { access: string }).access

      const authQuery = await db.query<[{
        id: string
        org_id: string
        user_id: string
        scopes: string[]
      }]>(`RETURN {
        id: $auth.id,
        org_id: $auth.org_id,
        user_id: $auth.user_id,
        scopes: $auth.scopes
      }`)

      const keyInfo = authQuery[0]
      if (!keyInfo?.org_id) {
        await db.close()
        return c.json({
          error: 'internal_error',
          message: 'Authentication succeeded but session details not found'
        }, 500)
      }

      await db.close()

      const expiresIn = 900
      const expiresAt = new Date(Date.now() + expiresIn * 1000).toISOString()

      return c.json({
        token: jwtToken,
        expires_at: expiresAt,
        expires_in: expiresIn,
        org_id: keyInfo.org_id.toString().replace('organizations:', ''),
        user_id: keyInfo.user_id.toString().replace('users:', ''),
        scopes: keyInfo.scopes || [],
        source: 'surrealdb' // Indicate legacy path
      })

    } finally {
      try { await db.close() } catch {}
    }

  } catch (error) {
    console.error('[auth] API key auth error:', error)
    return c.json({
      error: 'internal_error',
      message: 'Authentication failed'
    }, 500)
  }
})
```

## Benefits of This Approach

### 1. Unified Key Management
- All API keys generated in one place (identity-vessel)
- Consistent format and validation
- Single revocation mechanism

### 2. Performance
- <2ms validation (HMAC + Redis)
- No SurrealDB queries for key validation
- Scales horizontally (stateless)

### 3. Security
- Keys never stored in database
- Constant-time HMAC comparison
- Fast revocation via Redis cache
- Automatic expiration support

### 4. Developer Experience
- One API key works everywhere
- Generate keys via dashboard UI
- Clear error messages
- Consistent auth flow

### 5. Operational Simplicity
- Single service to monitor for auth
- Centralized logging and metrics
- Easy to add rate limiting
- Clear audit trail

## Rollback Plan

If issues arise, rollback is simple:

1. **Remove identity-vessel validation code**
   - The fallback to SurrealDB still works
   - No data loss or corruption

2. **Revert deployment**
   - Previous version continues using SurrealDB
   - Existing keys continue working

3. **Keep identity-vessel running**
   - No harm in having it available
   - Can retry integration later

## Questions to Resolve

1. **JWT Token Generation**: Should activity-api generate its own JWT or should identity-vessel return a token directly?
   - **Recommendation**: Activity-api generates JWT (current approach) for consistency with existing auth flows

2. **Metadata Storage**: Should we store key metadata in SurrealDB even though keys are HMAC-based?
   - **Recommendation**: Yes, store metadata for usage tracking and audit logs

3. **Rate Limiting**: Should rate limiting happen at identity-vessel or activity-api?
   - **Recommendation**: Both - identity-vessel for validation, activity-api for API usage

4. **Expiration**: How to handle key expiration if keys are stateless HMAC?
   - **Recommendation**: Store expiration in metadata, check during validation
