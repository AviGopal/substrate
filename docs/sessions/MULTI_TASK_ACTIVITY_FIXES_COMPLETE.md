## Bug #1: Self-Referencing Variable Defaults

### Problem
```json
{
  "variables": [
    {
      "name": "templateId",
      "default": "{{templateId}}"  // ← Circular reference!
    }
  ]
}
```

When merged, literal string `"{{templateId}}"` was used as the value.  
Interpolation then tried to replace `{{templateId}}` with `"{{templateId}}"`, leaving the placeholder intact.

### Solution
**Auto-generate from related variables:**
- Detect pattern: `{{templateId}}` as default for `templateId`
- Generate kebab-case from `templateName`
- Example: "My Template" → "my-template"

**Code**: `activity-template.ts` lines 1526-1556

### Result
✅ Task 1 now generates `templateId` automatically from `templateName`

## Bug #2: Variables Not Inherited Across Tasks

### Problem
```typescript
// Task 1 generates: { templateId: "my-template" }
// Task 2 calls mergeDefaultVariables() with only user variables
// Result: Task 2 doesn't have templateId!
```

Each task called `mergeDefaultVariables()` with only the original user-provided variables.  
Variables generated by previous tasks (like `templateId` from Task 1) were lost.

### Solution
**Accumulate variables across tasks:**
```typescript
let accumulatedVariables = { ...variables }

for each task:
  mergedVariables = mergeDefaultVariables(task, accumulatedVariables)
  // Execute task...
  accumulatedVariables = { ...mergedVariables }  // ← Pass to next task
```

**Code**: `activity.ts` lines 1746, 1979-1985

### Result
✅ Task 2+ now receive variables from previous tasks  
✅ `templateId` generated in Task 1 is available in Tasks 2-4

## Bug #3: Code Block Interpolation

### Problem
```
Task 3 prompt contains:
```json
{
  "name": "{{templateName}}",  // ← Real variable (should replace)
  "prompt": "Use {{variableName}} for interpolation"  // ← Example (should preserve)
}
```
Rule: If prompt has `{{foo}}`, include it  // ← Inline example (should preserve)
```

Original code couldn't distinguish between:
- **Real variables** in code blocks (should be replaced)
- **Documentation examples** in code blocks (should be tolerated)

### Solution
**Context-aware interpolation:**
1. Replace ALL provided variables (including in code blocks)
2. When checking for missing variables, filter out those in code contexts:
   - Fenced code blocks (```)
   - Inline code (`)
3. Only throw errors for missing variables in regular text

**Code**: `activity-template.ts` lines 1432-1456

### Result
✅ Real variables in code blocks: Replaced  
✅ Example variables in code blocks: Tolerated  
✅ Missing variables in regular text: Error thrown (safety preserved)

## Technical Details

### Variable Flow Across Tasks

```
User provides:
  { templateName: "My Feature", templateDescription: "...", ... }

Task 1 (gather-requirements):
  mergeDefaultVariables() auto-generates:
    templateId = "my-feature" (from templateName)
  Accumulated: { templateName, templateDescription, templateId, ... }

Task 2 (design-task-graph):
  Receives accumulated variables from Task 1
  Uses: {{templateId}}, {{templateName}}
  Accumulated: { ... same as Task 1 ... }

Task 3 (write-template-json):
  Receives accumulated variables
  Prompt contains:
    - Real: {{templateId}}, {{templateName}} → Replaced
    - Examples: {{variableName}}, {{foo}} → Tolerated
  Accumulated: { ... same ... }

Task 4 (register-with-backend):
  Receives accumulated variables
  Uses: {{templateId}}
  Ready to execute ✅
```

### Interpolation Decision Tree

```
Found {{variable}} in prompt:

Is variable provided?
  YES → Replace everywhere (including code blocks)
  NO → Check context:
    In fenced code block (```)? → Tolerate (no error)
    In inline code (`)? → Tolerate (no error)
    In regular text? → Throw error ❌
```

## Lessons Learned

### 1. Multi-Layered Bugs
What appeared to be one issue (task failures) was actually **three separate bugs** stacked on each other:
- Bug #1 caused Task 1 to fail
- Bug #2 caused Task 2+ to fail (after fixing Bug #1)
- Bug #3 caused Task 3 to fail (after fixing Bugs #1 & #2)

### 2. Template Design Issues
The template had several design problems:
- Self-references in defaults (anti-pattern)
- Undeclared variables used across tasks
- Interpolation syntax in documentation examples

### 3. Variable Inheritance Is Natural
Activities naturally want to build up context across tasks.  
The accumulation pattern matches how humans think about multi-step workflows.

### 4. Lifecycle Tracing Works
The detailed lifecycle tracing added in previous sessions **pinpointed each bug precisely**.  
This was critical for understanding the failure modes.

## Template Authoring Guidelines

### DO ✅

**Use accumulated context:**
```json
{
  "tasks": [
    { "prompt": "Generate {{outputFile}}" },
    { "prompt": "Test {{outputFile}}" }  // ← Uses value from Task 1
  ]
}
```

**Use examples in code blocks:**
```
Instructions: `{{variableName}}` will be replaced

Schema:
```json
{
  "prompt": "Use {{variableName}} for interpolation"
}
```
```

**Auto-generate from other variables:**
```json
{
  "name": "featureId",
  "default": "{{featureName}}"  // ← Auto-converted to kebab-case
}
```

### DON'T ❌

**Avoid exact self-references:**
```json
{
  "name": "templateId",
  "default": "{{templateId}}"  // ❌ Use "{{templateName}}" instead
}
```

**Don't rely on undeclared variables:**
```json
{
  "prompt": "Create {{undeclaredVariable}}",  // ❌ Will throw error
  "variables": []  // ❌ Must declare all variables
}
```

**Don't mix structural and example variables:**
```json
{
  "prompt": "Use {{realVariable}} and {{exampleVariable}}",  // ⚠️ Ambiguous
  "variables": [{ "name": "realVariable" }]
}
```
Better: Use different syntax for examples (`<<example>>` or `${example}`)
