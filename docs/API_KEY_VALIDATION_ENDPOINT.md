# API Key Validation Endpoint Documentation

**Identity Vessel - API Key Validation**

## Overview

The `/v1/keys/validate` endpoint is the canonical source of truth for validating API keys in the Metabob system. All services should use this endpoint to validate API keys.

**Endpoint:** `POST /v1/keys/validate`
**Base URL (Production):** `https://identity.metabob.com`
**Authentication:** None (this IS the authentication endpoint)

## Key Features

- **Fast Validation**: HMAC signature verification in <5ms (local computation, no network)
- **Revocation Check**: Redis-backed revocation list with 1-year TTL
- **Secure**: Constant-time signature comparison prevents timing attacks
- **Stateless**: No database lookup required for valid keys
- **Complete**: Returns org_id, user_id, key_id, scopes, and role

## Response Format

### Success Response (Valid Key)

**Status:** `200 OK`

```json
{
  "success": true,
  "data": {
    "valid": true,
    "org_id": "test_org_123",
    "user_id": "test_user_456",
    "key_id": "key_abcdefghijklmnop",
    "scopes": ["read", "write"],
    "role": "user"
  }
}
```

### Success Response (Invalid Key)

**Status:** `200 OK`

```json
{
  "success": true,
  "data": {
    "valid": false,
    "error": "Invalid API key format or signature"
  }
}
```

### Error Response (Malformed Request)

**Status:** `400 Bad Request`

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "Missing required field: api_key"
  }
}
```

## Response Fields

### When `valid: true`

| Field | Type | Description |
|-------|------|-------------|
| `valid` | boolean | Always `true` for valid keys |
| `org_id` | string | Organization ID extracted from the key |
| `user_id` | string | User ID extracted from the key |
| `key_id` | string | Unique key identifier (starts with `key_`) |
| `scopes` | string[] | Array of permission scopes (e.g., `["read", "write"]`) |
| `role` | string | User role (default: `"user"`) |

### When `valid: false`

| Field | Type | Description |
|-------|------|-------------|
| `valid` | boolean | Always `false` for invalid keys |
| `error` | string | Human-readable error message |

## Error Cases

### 1. Invalid Format

**Error:** `"Invalid API key format"`

**Cause:** The API key is not properly base64url-encoded, or doesn't contain 5 parts when decoded.

**Example:**
```bash
# Not base64url encoded
curl -X POST https://identity.metabob.com/v1/keys/validate \
  -H "Content-Type: application/json" \
  -d '{"api_key": "not-a-valid-key"}'

# Response:
{
  "success": true,
  "data": {
    "valid": false,
    "error": "Invalid API key format"
  }
}
```

### 2. Invalid Signature

**Error:** `"Invalid API key signature"`

**Cause:** The HMAC signature doesn't match the expected signature for the key's payload. This indicates the key has been tampered with or was not generated by identity-vessel.

**Example:**
```bash
# Tampered signature
curl -X POST https://identity.metabob.com/v1/keys/validate \
  -H "Content-Type: application/json" \
  -d '{"api_key": "bWJfdGVzdC10ZXN0X29yZ18xMjMtdGVzdF91c2VyXzQ1Ni1rZXlfYWJjZGVmZ2hpamtsbW5vcC10YW1wZXJlZDEyMzQ1Njc4OTAxMjM0NTY3ODkwMTI="}'

# Response:
{
  "success": true,
  "data": {
    "valid": false,
    "error": "Invalid API key signature"
  }
}
```

### 3. Revoked Key

**Error:** `"API key has been revoked"`

**Cause:** The key was explicitly revoked via the `/v1/keys/revoke` endpoint.

**Example:**
```bash
# First revoke the key
curl -X POST https://identity.metabob.com/v1/keys/revoke \
  -H "Content-Type: application/json" \
  -d '{"key_id": "key_abcdefghijklmnop"}'

# Then try to validate
curl -X POST https://identity.metabob.com/v1/keys/validate \
  -H "Content-Type: application/json" \
  -d '{"api_key": "bWJfdGVzdC10ZXN0X29yZ18xMjMtdGVzdF91c2VyXzQ1Ni1rZXlfYWJjZGVmZ2hpamtsbW5vcC1hMWIyYzNkNGU1ZjZnN2g4aTlqMGsxbDJtM240"}'

# Response:
{
  "success": true,
  "data": {
    "valid": false,
    "error": "API key has been revoked"
  }
}
```

### 4. Missing Parameter

**Status:** `400 Bad Request`

**Cause:** The `api_key` field is missing from the request body.

```bash
curl -X POST https://identity.metabob.com/v1/keys/validate \
  -H "Content-Type: application/json" \
  -d '{}'

# Response:
{
  "success": false,
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "Required field missing: api_key"
  }
}
```

## Validation Flow

The validation process has two stages:

### Stage 1: Format and Signature Validation (Fast Path)

**Duration:** <5ms (local computation, no network)

1. **Decode** from base64url to get raw key
2. **Parse** into 5 parts: `prefix`, `org_id`, `user_id`, `key_id`, `signature`
3. **Verify prefix** is either `mb_live` or `mb_test`
4. **Compute HMAC** signature from `prefix.org_id.user_id.key_id`
5. **Compare** with provided signature using constant-time comparison

If validation fails at this stage, the endpoint returns immediately with `valid: false`.

### Stage 2: Revocation Check (Network Call)

**Duration:** ~1-2ms (Redis lookup)

1. **Check Redis** for revoked key ID
2. If revoked, return `valid: false` with revocation error
3. If not revoked, return `valid: true` with key metadata

## Performance Characteristics

| Metric | Value | Notes |
|--------|-------|-------|
| **Average Latency** | 40-50ms | Includes network latency to canary deployment |
| **Local Validation** | <5ms | HMAC signature verification only |
| **Revocation Check** | 1-2ms | Redis lookup (in-cluster) |
| **Throughput** | ~20 req/sec/instance | Single-threaded Bun runtime |

**Note:** The performance test in our test suite shows ~48ms average, which includes:
- Network latency from client to canary (35-40ms)
- Actual validation time (5-8ms)
- Response serialization and transfer (2-5ms)

For local validation (HMAC signature only), expect <5ms consistently.

## Security Considerations

### 1. Constant-Time Comparison

The signature comparison uses Node.js's `timingSafeEqual` to prevent timing attacks:

```typescript
import { timingSafeEqual } from 'crypto';

// Prevents timing attacks by comparing all bytes
return timingSafeEqual(
  Buffer.from(providedSignature),
  Buffer.from(expectedSignature)
);
```

### 2. HMAC Signature

Keys use HMAC-SHA256 signatures with a secret key stored in environment variables:

```typescript
const signature = createHmac('sha256', SECRET_KEY)
  .update(payload)
  .digest('hex')
  .slice(0, 32);
```

### 3. Revocation Storage

Revoked keys are stored in Redis with 1-year TTL:

```typescript
await redis.set(`revoked:${keyId}`, '1', 'EX', 365 * 24 * 60 * 60);
```

### 4. No Database Lookup

Valid keys don't require database lookup, making the system:
- **Fast**: No network calls for valid keys (except Redis)
- **Scalable**: No database connection limit concerns
- **Resilient**: Works even if database is down

## Integration Examples

### TypeScript (Bun/Node.js)

```typescript
interface ValidationResult {
  valid: boolean;
  org_id?: string;
  user_id?: string;
  key_id?: string;
  scopes?: string[];
  role?: string;
  error?: string;
}

async function validateApiKey(apiKey: string): Promise<ValidationResult> {
  const response = await fetch('https://identity.metabob.com/v1/keys/validate', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ api_key: apiKey })
  });

  const data = await response.json();

  if (!response.ok) {
    throw new Error(`Validation failed: ${data.error?.message}`);
  }

  return data.data;
}

// Usage
const result = await validateApiKey('bWJfdGVzdC10ZXN0X29yZ18xMjMt...');
if (result.valid) {
  console.log(`Authenticated: org=${result.org_id}, user=${result.user_id}`);
  console.log(`Scopes: ${result.scopes?.join(', ')}`);
} else {
  console.error(`Invalid key: ${result.error}`);
}
```

### Middleware Pattern (Hono)

```typescript
import { Context, Next } from 'hono';

async function apiKeyAuth(c: Context, next: Next) {
  const authHeader = c.req.header('Authorization');
  if (!authHeader?.startsWith('Bearer ')) {
    return c.json({ error: 'Missing API key' }, 401);
  }

  const apiKey = authHeader.slice(7);
  const response = await fetch('https://identity.metabob.com/v1/keys/validate', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ api_key: apiKey })
  });

  const { data } = await response.json();

  if (!data.valid) {
    return c.json({ error: data.error || 'Invalid API key' }, 401);
  }

  // Attach auth context to request
  c.set('auth', {
    org_id: data.org_id,
    user_id: data.user_id,
    key_id: data.key_id,
    scopes: data.scopes,
  });

  await next();
}

// Use in route
app.get('/protected', apiKeyAuth, async (c) => {
  const auth = c.get('auth');
  return c.json({ message: 'Authenticated!', org_id: auth.org_id });
});
```

## FAQ

### Q: Why does validation return 200 for invalid keys?

**A:** The endpoint successfully performed the validation operation. The result of that validation is conveyed in the `valid` field. This prevents clients from treating validation failures as server errors.

### Q: What's the difference between format/signature errors and revocation?

**A:**
- **Format/signature errors**: The key is malformed or tampered with (fast path, <5ms)
- **Revocation errors**: The key was valid but has been explicitly revoked (requires Redis lookup, ~2ms)

### Q: Can I cache validation results?

**A:** You can cache valid results for a short period (30-60 seconds), but be aware that keys can be revoked at any time. For critical operations, always validate.

### Q: What happens if Redis is down?

**A:** If Redis is unavailable, the endpoint will fail to check revocation and may return an error. The service should have fallback behavior (e.g., assume not revoked, log error).

### Q: How do I know if a key is expired?

**A:** The validation endpoint doesn't check expiration. The caller is responsible for storing and checking expiration dates in their own database.

### Q: Why are scopes always `["read", "write"]`?

**A:** The current implementation returns default scopes. The caller should override this based on their own database records if they store custom scopes per key.

## Architecture Notes

**Identity-vessel is the SINGLE SOURCE OF TRUTH for API key operations.**

- **Key Generation**: `/v1/keys/generate` creates HMAC-signed keys
- **Key Validation**: `/v1/keys/validate` verifies format, signature, and revocation
- **Key Revocation**: `/v1/keys/revoke` marks keys as revoked in Redis

**Other services delegate to identity-vessel:**

- **user-vessel**: Calls identity-vessel to generate/revoke keys, stores metadata in SurrealDB
- **metabob-activity-api**: Calls identity-vessel to validate API keys in requests
- **MiniBob**: Calls identity-vessel during bootstrap to validate its API key

**The separation of concerns:**

- **identity-vessel**: Knows how to generate, validate, and revoke keys (cryptographic operations)
- **user-vessel**: Knows which keys exist, who owns them, and metadata (business logic)
- **Consumers**: Validate keys via identity-vessel, use org_id/user_id for authorization
