## Root Cause Analysis

### Hypothesis 1: Org ID Mismatch (Most Likely)

**Evidence**:
1. MiniBob includes `org_id` and `project_id` in trace data (mcp.ts:1319-1320):
   ```typescript
   const orgId = this.getOrgId()
   const projectId = this.getProjectId()
   ```

2. Backend uses multi-tenant isolation with org_id filtering

3. If org_id from MiniBob doesn't match org_id of activity templates, traces appear "lost"

**How to Verify**:
```bash
# Check org_id used by MiniBob
grep -r "getOrgId\|getProjectId" repos/minibob/src/mcp.ts

# Query backend with org_id filter
curl -H "Authorization: ApiKey $API_KEY" \
  "https://activity.metabob.com/v2/activities/traces"  # See all orgs
```

### Hypothesis 2: Vessel Registration Required

**Evidence**:
1. Bootstrap shows "⚠️ Vessel registration skipped"
2. Traces might require registered vessel_id
3. Backend might reject traces from unregistered vessels

**How to Verify**:
Check if `/v2/activities/execution-traces` requires vessel registration

### Hypothesis 3: Silent Backend Failure

**Evidence**:
1. MiniBob's `storeExecutionTrace` returns false on error but doesn't throw
2. Logs might not be visible in CI/CD
3. Backend could be returning 200 but not storing traces

**How to Verify**:
```bash
# Add explicit logging in workflow
bunx @metabob/minibob@latest --trace -vvv ...
# Check for "[MCP] Execution trace stored" or "[MCP] Failed to store execution trace"
```

### Hypothesis 4: Trace Cache (Less Likely)

**Evidence**:
1. MiniBob has offline trace caching (trace-cache.ts)
2. If backend is "unavailable", traces go to cache
3. Cache might not be syncing

**How to Verify**:
Check for cached traces in workflow artifacts or local cache files
