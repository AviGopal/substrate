# Library Learning System Examples

This directory contains examples demonstrating the Library Learning System in action.

## Quick Start Example

This example shows how to analyze the Helm deployment configuration in `repos/platform` and generate activities for Helm operations.

### Step 1: Analyze Helm Configuration

```bash
activity({
  templateId: "analyze-library-structure",
  variables: {
    library_path: "/home/avi/documents/work/exp-repo/metabob-devbob/repos/platform",
    library_name: "helm-platform",
    library_type: "deployment-tool",
    analysis_depth: "medium",
    tree_depth: 3
  },
  reason: "Understand Helm deployment patterns in repos/platform to create reusable deployment activities"
})
```

**Expected Output**:
- `analysis/helm-platform-structure.md` - Directory structure and Helmfile organization
- `analysis/helm-platform-api.md` - Helmfile commands and configuration patterns
- `analysis/helm-platform-patterns.md` - Deployment workflows and release management patterns
- `analysis/helm-platform-SUMMARY.md` - Activity conversion roadmap

### Step 2: Generate Activities

```bash
activity({
  templateId: "generate-library-activities",
  variables: {
    library_name: "helm-platform",
    activity_count: 3,
    registration_path: "templates/helm-platform",
    register_with_metabob: true
  },
  reason: "Generate activities for: deploy-environment, update-release, rollback-release"
})
```

**Expected Output**:
- `activities/helm-platform-activity-specs.md` - Detailed activity specifications
- `activities/helm-platform-deploy-environment.json` - Deploy to environment activity
- `activities/helm-platform-update-release.json` - Update release activity
- `activities/helm-platform-rollback-release.json` - Rollback activity
- `activities/helm-platform-INDEX.md` - Activity catalog
- `activities/helm-platform-USAGE.md` - Usage documentation

### Step 3: Use Generated Activities

```bash
# Deploy to staging
activity({
  templateId: "helm-platform-deploy-environment",
  variables: {
    environment: "staging",
    namespace: "staging",
    helmfile_path: "./repos/platform/environments",
    dry_run: false
  },
  reason: "Deploy platform services to staging environment"
})

# Update specific release
activity({
  templateId: "helm-platform-update-release",
  variables: {
    release: "metabob-api",
    environment: "staging",
    values_override: {
      "image.tag": "v1.2.3"
    }
  },
  reason: "Update metabob-api to version 1.2.3 in staging"
})

# Rollback if needed
activity({
  templateId: "helm-platform-rollback-release",
  variables: {
    release: "metabob-api",
    environment: "staging",
    revision: 5  # Rollback to revision 5
  },
  reason: "Rollback metabob-api due to performance issues in v1.2.3"
})
```

## What Gets Analyzed?

### Directory Structure
- Organization patterns (monorepo vs multi-repo)
- Component separation (services, configs, scripts)
- Naming conventions
- Configuration hierarchies

### API Surface
- **CLI Commands**: Available commands, options, flags
- **Configuration Files**: YAML, JSON, TOML structures
- **Environment Variables**: Required and optional vars
- **Entry Points**: Main executables and scripts

### Workflow Patterns
- **Deployment Workflows**: How deployments are performed
- **Configuration Patterns**: How configuration is managed
- **State Management**: How state transitions occur
- **Error Handling**: How errors are detected and recovered
- **Validation**: How correctness is verified

### Integration Points
- **Plugin Systems**: How functionality is extended
- **Hooks/Callbacks**: Event-driven patterns
- **Dependencies**: External requirements
- **Composition**: How components combine

## Generated Activity Characteristics

Activities generated by this system have:

✅ **Clear State Transitions**: Before state → After state
✅ **Parameterized Variables**: Flexible configuration
✅ **Comprehensive Validation**: File checks, pattern matches, command verification
✅ **Error Handling**: Detection, recovery, rollback
✅ **Task Decomposition**: Logical sub-steps with dependencies
✅ **Retry Logic**: Resilient execution
✅ **Documentation**: Clear descriptions and examples

## Tips for Best Results

### Choosing Analysis Depth

- **Shallow (Quick, 5-10 min)**: Directory structure, major components, entry points
  - Use for: Quick exploration, initial assessment
  
- **Medium (Standard, 15-30 min)**: Full structure, API documentation, common patterns
  - Use for: Most libraries, balanced depth
  
- **Deep (Comprehensive, 30-60 min)**: Everything + rare patterns, edge cases, plugins
  - Use for: Critical infrastructure, complex systems

### Selecting Activity Count

Start with **2-3 high-value activities**:
- Most frequently used workflows
- Clear state transitions
- Well-documented patterns
- Composable operations

Avoid generating too many activities at once - iterate based on usage.

### Library Types

Choose the right library_type for better pattern extraction:

- `deployment-tool`: Helm, Terraform, Ansible, Docker Compose
- `cloud-provider`: AWS SDK, GCP SDK, Azure SDK
- `framework`: Express, Django, Rails, Spring Boot
- `cli-tool`: kubectl, aws-cli, gh, gcloud
- `build-tool`: Webpack, Vite, Gradle, Maven

## Workflow Composition

Generated activities can be composed into workflows:

```bash
# Full deployment workflow
const deployPipeline = async () => {
  // 1. Validate configuration
  await activity({ templateId: "helm-validate-config", ... });
  
  // 2. Deploy to staging
  await activity({ templateId: "helm-deploy-environment", variables: { environment: "staging" }, ... });
  
  // 3. Run smoke tests
  await activity({ templateId: "helm-test-release", ... });
  
  // 4. Deploy to production
  await activity({ templateId: "helm-deploy-environment", variables: { environment: "production" }, ... });
  
  // 5. Verify deployment
  await activity({ templateId: "helm-verify-deployment", ... });
};
```

## Troubleshooting

### Analysis Produces No Patterns

**Possible Causes**:
- Library has non-standard structure
- Documentation is minimal
- No examples or tests present

**Solutions**:
- Use deep analysis
- Manually review library first
- Focus on specific components

### Generated Activities Fail Validation

**Possible Causes**:
- Variable mismatches
- Circular dependencies
- Invalid JSON syntax

**Solutions**:
- Review `activities/[lib]-VALIDATION.md`
- Check `jq` output for JSON errors
- Verify variable references

### Activities Don't Match Expectations

**Possible Causes**:
- Analysis missed key patterns
- Activity count too low
- Wrong patterns prioritized

**Solutions**:
- Review analysis documents manually
- Increase activity_count
- Re-run with different analysis_depth
- Manually edit generated activities
