## Finding 1: Queue flooding is BOTH architecture AND configuration — the architecture has no drain

**Claim in spec**: (implicit) The boredom system supports substrate self-improvement by running named topology templates.

**Observed reality**:

The critical queue contains 1232 tasks, all auto-generated by the `TaskGenerator` service in `activity-api`. The generator runs every 5 minutes (`TASK_GENERATION_INTERVAL = 5 * 60 * 1000`) and is controlled by `TASK_GENERATION_ENABLED` (defaults to `true` — not disabled in substrate env).

The generator detects templates with low success rates and generates `debug__` goals, slow templates and generates `optimize_` goals, and periodically generates `inspect_` goals. Since `_goal_resolve` has 0% success rate and `improvise` is 2.9x slower than average, the generator fires at every 5-minute tick and emits up to 10 tasks per cycle.

**Observed task breakdown (critical queue)**:
- `debug__resolve` (291) — targeting `_goal_resolve` 0% success rate
- `debug__execute` (250) — targeting improvisation:tool:* executions
- `debug_lth-tick` (243), `debug_age-tick` (243), `debug_n-matrix` (204) — targeting sub-templates with low success

**Medium queue**:
- `optimize_y-driven` (302), `optimize_mprovise` (302) — improvise slowness
- `optimize_th-check` (8), `inspect_validation-audit` (7)

**Critical structural problem**: The boredom executor dequeues ONE task per poll cycle, then executes it (via `SearchFirstExecutor`) and waits for completion before polling again. Each `SearchFirst` execution on a `debug__resolve` goal takes ~8-10 minutes (3 attempts × ~3 min each, budget 150k tokens). The task generator adds 10 tasks every 5 minutes. The drain rate (1 task per 8-10 minutes) is permanently slower than the fill rate (10 tasks per 5 minutes). The queue will grow indefinitely.

**The architecture problem**: There is no mechanism to DRAIN the queue when it floods. `fetchTask()` dequeues one task, REMOVES it from Redis, then the executor runs it. If it fails, the task is gone (not re-enqueued). But the generator creates a fresh version 5 minutes later with the same root cause still unaddressed. The queue grows because failures are not resolved — the `_goal_resolve` failure persists, generating new `debug__` tasks forever.

**The configuration problem**: `TASK_GENERATION_ENABLED` is not set to `false` in the substrate's `/etc/substrate/env`. This is a single-line fix that would stop new task generation immediately.

**Gap type**: claim_incorrect (spec implies named topology templates are what runs; reality is goal-based debug tasks dominate 100% of actual execution)
**Severity**: blocking

**Proposed action**: Add `TASK_GENERATION_ENABLED=false` to `/etc/substrate/env` and restart activity-api. This stops the flood immediately. Separate from that, the `_goal_resolve` 0% success rate root cause needs fixing so even if task generation is re-enabled, it doesn't flood.

However, this task ID does NOT appear in either `boredom:queue:critical` or `boredom:queue:medium`. The task data exists but it is not in any queue sorted set, so `fetchTask()` will never return it. Only the 1232 auto-generated `debug__*` tasks are in the queues.

**Gap type**: claim_incorrect (dev coordination states topology tasks are queued; they are not dequeue-reachable)

**Proposed action**: The `topology_harness_next` key's content shows `templateId:` format is set correctly. The fix is to call `enqueueTask()` (i.e., do the `ZADD` into `boredom:queue:critical`) with this task. Either the enqueue script ran but its `zadd` failed silently, or it didn't run. ## Finding 3: minibob is processing debug__resolve goal via SearchFirst, not topology templates

**Observed reality**:

Minibob log at observation time (2026-05-25T00:34-00:44Z) shows:
- `[SearchFirst] Starting goal: Investigate why activity "_goal_resolve" has 0% success rate after 7 executions...`
- `[SearchFirst] Best match score (0) below threshold 0.3 - will improvise`
- 4 sequential attempts all fail at step-1 with `Required file missing: error_analysis.md` (then `error_analysis.json`)
- Each attempt exhausts budget: `Budget used: 1575341 tokens (1050%)`

The failure pattern is structural: the goal requires creating a file `error_analysis.md` as output, but the LLM improvisation doesn't reliably produce this file even after 4 recovery attempts. This is the `_goal_resolve` failure generating the debug task that is generating the improvise attempts that are the slow templates, which generate `optimize_mprovise` tasks.

**The feedback loop**:
1. `_goal_resolve` fails → TaskGenerator detects 0% success → generates `debug__resolve` task
2. `debug__resolve` runs via SearchFirst → improvise path → fails → generates new `debug__execute` task
3. `improvise` template has 2.9x avg duration → TaskGenerator detects slow → generates `optimize_mprovise` task
4. Cycle repeats every 5 minutes, adding 5-10 tasks each time

**Gap type**: claim_incorrect (minibob is executing self-referential debug goals, not topology templates)
**Severity**: blocking

The ias-executor path activates via `GOAL_RUNTIME=ias-executor` only when a goal is submitted through the standard goal-processing flow, not through SearchFirst.

The topology template `topology_harness_next` HAS `templateId: "development-vessel:harness-run-matrix"` which WOULD route through GoalHost via the templateId path in `executeTask()`. But this task is not in the queue.

**Gap type**: coverage_gap (the fix is deployed but the execution path that exercises it is not being reached)
**Severity**: blocking for S.4a (coverage_progress requires Thompson posteriors to move, which requires GoalHost's composition_chain to propagate, which requires templateId tasks to execute)

**Proposed action**: Get `topology_harness_next` (and the other 4 topology tasks) into `boredom:queue:critical` via `zadd`. Then templateId-based execution will route through GoalHost → ias-executor → composition_chain populated → Thompson updates.

## Finding 5: Does explicit vessel architecture fix queue flooding?

**Question**: Does the explicit vessel architecture (local-tools-vessel, goal-vessel) actually fix the queue flooding?

**Assessment**: No, not directly. The queue flooding is caused by:
1. `TaskGenerator` running every 5 minutes and detecting `_goal_resolve` failures
2. The drain rate (1 task per 8-10 min) being permanently slower than fill rate (10 tasks per 5 min)

The substrate-explicit-vessels spec (`openspec/changes/2026-05-23-substrate-explicit-vessels/design.md`) addresses vessel unbundling and cross-vessel dispatch for topology discovery. It does NOT modify `TaskGenerator` logic. Even with explicit vessels deployed, if `_goal_resolve` continues failing and `TASK_GENERATION_ENABLED=true`, the same flood would occur.

The explicit vessel architecture is valuable for S.4a (composition_chain threading across vessels, vessel identity) but it is not the fix for the queue flooding.

**Minimum change to fix queue flooding**: Set `TASK_GENERATION_ENABLED=false` in `/etc/substrate/env`. This stops new task generation. The existing 1232 tasks will drain over time (or can be flushed via `DEL boredom:queue:critical boredom:queue:medium`). This is a 2-line change; explicit vessel architecture is months of work.

## Finding 6: gap-006 — can substrate describe its own operation?

**Claim in spec / gap-006**: The substrate cannot self-describe its own operation or detect its own stagnation.

**Updated assessment (post-dev-fixes)**:

Gap-006 was initially recorded when the substrate had 6+ hours of identical failures with no deviation. Dev's fixes (cache bug 93cd621, embedding EMBEDDING_MODEL_DIR, templateId boredom format) partially addressed the underlying causes. The coordination state shows partial recovery.

However, based on current observation (2026-05-25T00:45Z):

**What the substrate CANNOT describe:**
- Why the boredom queue has 1232 tasks (no aggregate progress meta-concept)
- Why `_goal_resolve` has 0% success rate after 291+ debug attempts (no causal-chain idiom linking TaskGenerator output to execution failures)
- Why the topology harness task exists in Redis but isn't being executed (no queue-integrity awareness)
- That it's in a debug-loop spending ~$3/hr investigating its own failures rather than running topology discovery

**What the substrate CAN describe:**
- Individual execution traces (execution-traces endpoint works)
- Template registry (18 templates stable)
- Thompson posteriors for named templates (though they show alpha=beta=1 = no update)
- Embedding status (healthy per health endpoint)

**Evidence for gap-006's core claim**: The substrate IS executing. It IS recording traces. But it cannot detect that "291 debug__resolve executions, 0 topology discoveries" represents 24 hours of spinning without S.4a progress. The meta-measurement (reachable_learned monotonically increasing) would detect this — but that measurement lives in coverage-tick's output, which is not executing because the topology task is not in the queue.

**Verdict**: gap-006 `claim_incorrect` severity remains BLOCKING. The substrate's own self-measurement primitives (coverage-tick, substrate-health-tick) are registered and working, but they are not running because the queue is flooded with debug tasks that have priority "critical" and the topology tasks are not enqueued. The substrate cannot detect this condition from its own state.

## Finding 7: Minimum change needed to get topology discovery running

**Three sequential changes, ordered by immediacy:**

### Change A (immediate, ~2 minutes, no restart needed):
```bash
docker exec substrate-live redis-cli DEL boredom:queue:critical boredom:queue:medium
# Then re-enqueue the 5 topology tasks:
docker exec substrate-live curl -s -X POST http://localhost:8080/v2/activities/boredom/enqueue \
  -H "Content-Type: application/json" \
  -H "Authorization: ApiKey <SUBSTRATE_API_KEY>" \
  -d '{"templateId":"development-vessel:coverage-tick","priority":"critical","variables":{},"reason":"Topology: measure coverage"}'
# Repeat for the other 4 topology templates
```
This clears the 1851 auto-generated tasks and puts topology templates at the front of the queue.

### Change B (prevents re-flooding, requires restart):
Add `TASK_GENERATION_ENABLED=false` to `/etc/substrate/env`. Then `systemctl restart activity-api`. This stops the TaskGenerator from re-flooding the queue when topology templates start running and `_goal_resolve` still shows 0% success.

### Change C (prerequisite for S.4a progress, requires restart):
Verify `_goal_resolve` failure root cause. Current evidence: 291+ debug executions, all failing at step-1 of SearchFirst with "Required file missing". The `_goal_resolve` template itself needs either (a) a valid template that executes correctly, or (b) the goal-processing pipeline fix that makes `_goal_resolve` succeed when the named template runs successfully. This is the gap-007 composition_chain / Thompson issue.

**Without Change C, even after Changes A+B**, topology templates will run, coverage-tick will emit coverageReports, but `_goal_resolve` will continue failing (albeit silently with TASK_GENERATION_ENABLED=false). The S.4a gate requires `coverage_progress=true` for 3 consecutive emissions — this depends on coverage-tick actually measuring progress, which depends on Thompson posteriors updating, which depends on composition_chain being populated, which depends on templateId execution via GoalHost. Changes A+B create the conditions for Change C's verification.
