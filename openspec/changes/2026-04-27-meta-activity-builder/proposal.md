## Why

The impulse-activity loop is functional in production (Phase 8: 4/5 ✅). The natural next move is **registry quality**: replacing the 2,500+ existing templates with idiomatically-aligned activities generated by the impulse-activity system itself.

Rather than hand-curating each replacement, we author a **meta-activity that creates activities** (`make-activity`). This activity:
- Is itself idiomatic (declared input/output shapes, uses resolvers, validates goal completion via the validator-dispatch lifecycle)
- Composes other activities (sub-goal decomposition via `activity` resolver dispatching child activities)
- Uses tools-from-impulses (LLM resolver receives MCP tools surfaced as impulses; impulses can also surface vessel-provided functions)
- Iterates over candidate approaches via a new **iteration resolver** primitive (closing F-4 / Infra Gap B)
- Persists its output as a new activity template (`activityTemplate_write` write resolver)
- Self-bounds to a sandboxed working directory (default `/tmp/`)

Long-term, this creates a learning arc: the LLM's typical patterns inside `make-activity` invocations are observed, ribosome-extracted, and over time converted into cheaper deterministic resolvers or vessel-owned functions. The impulse-activity system becomes a self-improving template factory.

## What Changes

### 1. Iteration resolver (closes F-4 / Infra Gap B)

A new template-dispatchable resolver that loops over a list-shaped impulse, executing a body for each element. Input: a list-bearing impulse + a body specification (sub-resolver call or sub-activity dispatch). Output: a list-bearing output impulse with per-iteration results, and a per-iteration failure_mode taxonomy.

The iteration body honors the same impulse-pool conventions as parent task (input/output shapes), so iteration over `activityRecommendations` (each entry an activity candidate) can dispatch each candidate via `activity` resolver and aggregate results.

### 2. `make-activity` meta-activity template

**Input shapes**: `goal`, `activityRecommendations`, `mcpTool`
**Output shapes**: `goalEnd` (always), plus dynamically-discovered shapes from sub-activity output_shapes

**Tasks** (rough sketch — author to refine):

1. **`acquire_context`**: read `goal` impulse + relevant existing activities via `activityTemplate` impulse-resolve
2. **`identify_candidates`**: `activityRecommendations` impulse → iterate each via the new iteration resolver; LLM scores each against the goal; outputs `candidate_plan` impulse
3. **`execute_plan`**: dispatch chosen activities via `activity` resolver. Tools include:
   - Resolver-driven steps (bash, file, edit, git) for deterministic operations
   - LLM resolver with tool-from-impulse subset (MCP tools, vessel-provided functions)
   - `activity` resolver for sub-goal dispatch
4. **`handle_errors`**: on any sub-task failure, iterate alternate approaches (small variant set) before giving up
5. **`declare_complete`**: explicit LLM tool call (e.g., `goalEnd` synthesizer) that emits the `goalEnd` impulse — independent of the validator-dispatch verdict
6. **`extract_template`**: ribosome extraction from the successful execution path → emit new activity template via `activityTemplate_write`

### 3. Sandbox safety

The activity's bash/file resolvers are constrained to a specified `workingDirectory` (default `/tmp/<goal-id>/`). Any path-affecting operation outside this directory must be:
- Explicitly listed in the activity's `allowed_external_paths` (none by default)
- OR rejected with a `safety_breach` failure_mode

A test verifies a probe run with the meta-activity does not produce file changes outside `/tmp/`.

## Capabilities

### New Capabilities

- **`iteration-resolver`** — generic foreach/while primitive callable from activity JSON templates. Closes F-4 (deferred Infra Gap B).
- **`meta-activity-builder`** — `make-activity` template that produces new activity templates from goal+recommendations input.
- **`sandbox-enforcement`** — working-directory constraint on bash/file resolvers.

## Impact

- **minibob**: new resolver registration + new embedded template + sandbox path checks in bash/file resolvers + tests.
- **activity-api**: no schema changes (uses existing `activityTemplate_write`).
- **Workbench**: out of scope (will follow post-spec).

## Success criteria

The meta-activity-builder is considered complete when:

1. **`make-activity` runs** against a sample goal in `/tmp/<goal-id>/` and reports `goalEnd` impulse + verifier confirmation.
2. **A new activity template** is registered in the backend (`activityTemplate_write` succeeded) reflecting the executed plan.
3. **Sandbox holds**: `find / -newer <baseline-marker> -type f 2>/dev/null | grep -v /tmp/` is empty post-run.
4. **Iteration primitive validated**: at least one `make-activity` invocation iterates over `activityRecommendations` of length ≥ 2.
5. **Composition observed**: the trace shows the meta-activity dispatching at least one sub-activity via the `activity` resolver, with both nested traces persisting.
