<section data-mw-section-id="4" id="mwSQ" aria-labelledby="Dirty_reads"><div class="mw-heading mw-heading3"><h3 id="Dirty_reads">Dirty reads</h3><span class="mw-editsection"><span class="mw-editsection-bracket">[</span><a href="/w/index.php?title=Isolation_(database_systems)&amp;action=edit&amp;section=4" title="Edit section: Dirty reads"><span>edit</span></a><span class="mw-editsection-bracket">]</span></span></div>
<span class="mw-empty-elt" about="#mwt8" typeof="mw:Transclusion" id="mwSg" data-mw='{"parts":[{"template":{"target":{"wt":"Main","href":"./Template:Main"},"params":{"1":{"wt":"Write-read conflict"}},"i":0}}]}'><style data-mw-deduplicate="TemplateStyles:r1368532237" typeof="mw:Extension/templatestyles" about="#mwt9" data-mw='{"name":"templatestyles","attrs":{"src":"Module:Hatnote/styles.css"},"body":{"extsrc":""}}'>.mw-parser-output .hatnote{font-style:italic}.mw-parser-output div.hatnote{padding-left:1.6em;margin-bottom:0.5em}.mw-parser-output .hatnote i{font-style:normal}.mw-parser-output .hatnote+.mw-empty-elt+.hatnote{margin-top:-0.5em}@media print{body.ns-0 .mw-parser-output .hatnote{display:none!important}}</style></span><div role="note" class="hatnote navigation-not-searchable" about="#mwt8" id="mwSw">Main article: <a rel="mw:WikiLink" href="https://en.wikipedia.org/wiki/Write-read_conflict" title="Write-read conflict" class="mw-redirect">Write-read conflict</a></div>

<p id="mwTA">A <i id="mwTQ">dirty read</i> (aka <i id="mwTg">uncommitted dependency</i>) occurs when a transaction retrieves a row that has been updated by another transaction that is not yet committed.</p>

<p id="mwTw">In this example, transaction 1 retrieves the row with id 1, then transaction 2 updates the row with id 1, and finally transaction 1 retrieves the row with id 1 again. Now if transaction 2 rolls back its update (already retrieved by transaction 1) or performs other updates, then the view of the row may be wrong in transaction 1. At the READ UNCOMMITTED isolation level, the second SELECT in transaction 1 retrieves the updated row: this is a dirty read. At the READ COMMITTED, REPEATABLE READ, and SERIALIZABLE isolation levels, the second SELECT in transaction 1 retrieves the initial row.</p>

</section><section data-mw-section-id="5" id="mwrw" aria-labelledby="Non-repeatable_reads"><div class="mw-heading mw-heading3"><h3 id="Non-repeatable_reads">Non-repeatable reads</h3><span class="mw-editsection"><span class="mw-editsection-bracket">[</span><a href="/w/index.php?title=Isolation_(database_systems)&amp;action=edit&amp;section=5" title="Edit section: Non-repeatable reads"><span>edit</span></a><span class="mw-editsection-bracket">]</span></span></div>
<p id="mwsA">A <i id="mwsQ">non-repeatable read</i> occurs when a transaction retrieves a row twice and that row is updated by another transaction that is committed in between.</p>

<p id="mwsg">In this example, transaction 1 retrieves the row with id 1, then transaction 2 updates the row with id 1 and is committed, and finally transaction 1 retrieves the row with id 1 again. At the READ UNCOMMITTED and READ COMMITTED isolation levels, the second SELECT in transaction 1 retrieves the updated row: this is a non-repeatable read. At the REPEATABLE READ and SERIALIZABLE isolation levels, the second SELECT in transaction 1 retrieves the initial row.</p>

</section><section data-mw-section-id="6" id="mwAQo" aria-labelledby="Phantom_reads"><div class="mw-heading mw-heading3"><h3 id="Phantom_reads">Phantom reads</h3><span class="mw-editsection"><span class="mw-editsection-bracket">[</span><a href="/w/index.php?title=Isolation_(database_systems)&amp;action=edit&amp;section=6" title="Edit section: Phantom reads"><span>edit</span></a><span class="mw-editsection-bracket">]</span></span></div>
<p id="mwAQs">A <i id="mwAQw">phantom read</i> occurs when a transaction retrieves a set of rows twice and new rows are inserted into or removed from that set by another transaction that is committed in between.</p>

<p id="mwAQ0">In this example, transaction 1 retrieves the set of rows with age greater than 17, then transaction 2 inserts a row with age 26 and is committed, and finally transaction 1 retrieves the set of rows with age greater than 17 again. At the READ UNCOMMITTED, READ COMMITTED, and REPEATABLE READ isolation levels, the second SELECT in transaction 1 retrieves the new set of rows that includes the inserted row: this is a phantom read. At the SERIALIZABLE isolation level, the second SELECT in transaction 1 retrieves the initial set of rows.</p>

<p id="mwAWI">There are two basic strategies used to prevent non-repeatable reads and phantom reads. In the first strategy, <i id="mwAWM">lock-based concurrency control</i>, transaction 2 is committed after transaction 1 is committed or rolled back. It produces the serial <a rel="mw:WikiLink" href="https://en.wikipedia.org/wiki/Database_transaction_schedule" title="Database transaction schedule" id="mwAWQ">schedule</a> <i id="mwAWU">T1, T2</i>. In the other strategy, <i id="mwAWY"><a rel="mw:WikiLink" href="https://en.wikipedia.org/wiki/Multiversion_concurrency_control" title="Multiversion concurrency control" id="mwAWc">multiversion concurrency control</a></i>, transaction 2 is committed immediately while transaction 1, which started before transaction 2, continues to operate on an old snapshot of the database taken at the start of transaction 1, and when transaction 1 eventually tries to commit, if the result of committing would be equivalent to the serial schedule <i id="mwAWg">T1, T2</i>, then transaction 1 is committed; otherwise, there is a commit conflict and transaction 1 is rolled back with a serialization failure.</p>

<p id="mwAWk">Under lock-based concurrency control, non-repeatable reads and phantom reads may occur when read locks are not acquired when performing a SELECT, or when the acquired locks on affected rows are released as soon as the SELECT is performed. Under multiversion concurrency control, non-repeatable reads and phantom reads may occur when the requirement that a transaction affected by a commit conflict must be rolled back is relaxed.</p>

</section></section><section data-mw-section-id="7" id="mwAWo" aria-labelledby="Isolation_levels"><div class="mw-heading mw-heading2"><h2 id="Isolation_levels">Isolation levels</h2><span class="mw-editsection"><span class="mw-editsection-bracket">[</span><a href="/w/index.php?title=Isolation_(database_systems)&amp;action=edit&amp;section=7" title="Edit section: Isolation levels"><span>edit</span></a><span class="mw-editsection-bracket">]</span></span></div>
<p id="mwAWs">Of the four <a rel="mw:WikiLink" href="https://en.wikipedia.org/wiki/ACID" title="ACID" id="mwAWw">ACID</a> properties in a <a rel="mw:WikiLink" href="https://en.wikipedia.org/wiki/Database_management_system" title="Database management system" class="mw-redirect" id="mwAW0">DBMS</a> (Database Management System), the isolation property is the one most often relaxed.  When attempting to maintain the highest level of isolation, a DBMS usually acquires <a rel="mw:WikiLink" href="https://en.wikipedia.org/wiki/Lock_(database)" title="Lock (database)" class="mw-redirect" id="mwAW4">locks</a> on data which may result in a loss of <a rel="mw:WikiLink" href="https://en.wikipedia.org/wiki/Concurrency_(computer_science)" title="Concurrency (computer science)" id="mwAW8">concurrency</a>, or implements <a rel="mw:WikiLink" href="https://en.wikipedia.org/wiki/Multiversion_concurrency_control" title="Multiversion concurrency control" id="mwAXA">multiversion concurrency control</a>. This requires adding logic for the <a rel="mw:WikiLink" href="https://en.wikipedia.org/wiki/Software_application" title="Software application" class="mw-redirect" id="mwAXE">application</a> to function correctly.</p>

<p id="mwAXI">Most DBMSs offer a number of <i id="mwAXM">transaction isolation levels</i>, which control the degree of locking that occurs when selecting data. For many database applications, the majority of database transactions can be constructed to avoid requiring high isolation levels (e.g. SERIALIZABLE level), thus reducing the locking overhead for the system.  The programmer must carefully analyze database access code to ensure that any relaxation of isolation does not cause software bugs that are difficult to find. Conversely, if higher isolation levels are used, the possibility of <a rel="mw:WikiLink" href="https://en.wikipedia.org/wiki/Deadlock_(computer_science)" title="Deadlock (computer science)" id="mwAXQ">deadlock</a> is increased, which also requires careful analysis and programming techniques to avoid.</p>

<p id="mwAXU">Since each isolation level is stronger than those below, in that no higher isolation level allows an action forbidden by a lower one, the standard permits a DBMS to run a transaction at an isolation level stronger than that requested (e.g., a "Read committed" transaction may actually be performed at a "Repeatable read" isolation level).</p>

<p id="mwAXY">The isolation levels defined by the <a rel="mw:WikiLink" href="https://en.wikipedia.org/wiki/American_National_Standards_Institute" title="American National Standards Institute" id="mwAXc">ANSI</a>/<a rel="mw:WikiLink" href="https://en.wikipedia.org/wiki/International_Organization_for_Standardization" title="International Organization for Standardization" id="mwAXg">ISO</a> <a rel="mw:WikiLink" href="https://en.wikipedia.org/wiki/SQL" title="SQL" id="mwAXk">SQL</a> standard are listed as follows.</p>

<section data-mw-section-id="8" id="mwAXo" aria-labelledby="Serializable"><div class="mw-heading mw-heading3"><h3 id="Serializable">Serializable</h3><span class="mw-editsection"><span class="mw-editsection-bracket">[</span><a href="/w/index.php?title=Isolation_(database_systems)&amp;action=edit&amp;section=8" title="Edit section: Serializable"><span>edit</span></a><span class="mw-editsection-bracket">]</span></span></div>
<p id="mwAXs">This is the <i id="mwAXw">highest</i> isolation level.</p>

<p id="mwAX0">With a lock-based <a rel="mw:WikiLink" href="https://en.wikipedia.org/wiki/Concurrency_control" title="Concurrency control" id="mwAX4">concurrency control</a> DBMS implementation, <a rel="mw:WikiLink" href="https://en.wikipedia.org/wiki/Serializability" title="Serializability" class="mw-redirect" id="mwAX8">serializability</a> requires read and write locks (acquired on selected data) to be released at the end of the transaction.  Also <i id="mwAYA">range-locks</i> must be acquired when a <a rel="mw:WikiLink" href="https://en.wikipedia.org/wiki/Select_(SQL)" title="Select (SQL)" id="mwAYE">SELECT</a> query uses a ranged <i id="mwAYI">WHERE</i> clause, especially to avoid the <i id="mwAYM"><b id="mwAYQ"><a rel="mw:WikiLink" href="#Phantom_reads" class="mw-selflink-fragment" id="mwAYU">phantom reads</a></b></i> phenomenon.</p>

<p id="mwAYY">When using non-lock based concurrency control, no locks are acquired; however, if the system detects a <i id="mwAYc">write collision</i> among several concurrent transactions, only one of them is allowed to commit.  See <i id="mwAYg"><a rel="mw:WikiLink" href="https://en.wikipedia.org/wiki/Snapshot_isolation" title="Snapshot isolation" id="mwAYk">snapshot isolation</a></i> for more details on this topic.</p>

<p id="mwAYo">From<span typeof="mw:DisplaySpace" id="mwAYs"> </span>: (Second Informal Review Draft) ISO/IEC 9075:1992, Database Language SQL- July 30, 1992:
<i id="mwAYw">The execution of concurrent SQL-transactions at isolation level SERIALIZABLE is guaranteed to be serializable. A serializable execution is defined to be an execution of the operations of concurrently executing SQL-transactions that produces the same effect as some serial execution of those same SQL-transactions. A serial execution is one in which each SQL-transaction executes to completion before the next SQL-transaction begins.</i></p>

</section><section data-mw-section-id="9" id="mwAY0" aria-labelledby="Repeatable_reads"><div class="mw-heading mw-heading3"><h3 id="Repeatable_reads">Repeatable reads</h3><span class="mw-editsection"><span class="mw-editsection-bracket">[</span><a href="/w/index.php?title=Isolation_(database_systems)&amp;action=edit&amp;section=9" title="Edit section: Repeatable reads"><span>edit</span></a><span class="mw-editsection-bracket">]</span></span></div>
<p id="mwAY4">In this isolation level, a lock-based <a rel="mw:WikiLink" href="https://en.wikipedia.org/wiki/Concurrency_control" title="Concurrency control" id="mwAY8">concurrency control</a> DBMS implementation keeps read and write locks (acquired on selected data) until the end of the transaction.  However, <i id="mwAZA">range-locks</i> are not managed, so <i id="mwAZE"><b id="mwAZI"><a rel="mw:WikiLink" href="#Phantom_reads" class="mw-selflink-fragment" id="mwAZM">phantom reads</a></b></i> can occur.</p>

<p id="mwAZQ">Write skew is possible at this isolation level in some systems. Write skew is a phenomenon where two writes are allowed to the same column(s) in a table by two different writers (who have previously read the columns they are updating), resulting in the column having data that is a mix of the two transactions.<sup about="#mwt22" class="mw-ref reference" id="cite_ref-3" rel="dc:references" typeof="mw:Extension/ref" data-mw='{"name":"ref","attrs":{},"body":{"id":"mw-reference-text-cite_note-3"}}'><a href="#cite_note-3" id="mwAZU"><span class="mw-reflink-text" id="mwAZY"><span class="cite-bracket" id="mwAZc">[</span>3<span class="cite-bracket" id="mwAZg">]</span></span></a></sup><sup about="#mwt25" class="mw-ref reference" id="cite_ref-4" rel="dc:references" typeof="mw:Extension/ref" data-mw='{"name":"ref","attrs":{},"body":{"id":"mw-reference-text-cite_note-4"}}'><a href="#cite_note-4" id="mwAZk"><span class="mw-reflink-text" id="mwAZo"><span class="cite-bracket" id="mwAZs">[</span>4<span class="cite-bracket" id="mwAZw">]</span></span></a></sup></p>

</section><section data-mw-section-id="10" id="mwAZ0" aria-labelledby="Read_committed"><div class="mw-heading mw-heading3"><h3 id="Read_committed">Read committed</h3><span class="mw-editsection"><span class="mw-editsection-bracket">[</span><a href="/w/index.php?title=Isolation_(database_systems)&amp;action=edit&amp;section=10" title="Edit section: Read committed"><span>edit</span></a><span class="mw-editsection-bracket">]</span></span></div>
<p id="mwAZ4">In this isolation level, a lock-based <a rel="mw:WikiLink" href="https://en.wikipedia.org/wiki/Concurrency_control" title="Concurrency control" id="mwAZ8">concurrency control</a> DBMS implementation keeps write locks (acquired on selected data) until the end of the transaction, but read locks are released as soon as the <a rel="mw:WikiLink" href="https://en.wikipedia.org/wiki/Select_(SQL)" title="Select (SQL)" id="mwAaA">SELECT</a> operation is performed (so the <i id="mwAaE"><b id="mwAaI"><a rel="mw:WikiLink" href="#Non-repeatable_reads" class="mw-selflink-fragment" id="mwAaM">non-repeatable reads phenomenon</a></b></i> can occur in this isolation level). As in the previous level, <i id="mwAaQ">range-locks</i> are not managed.</p>

<p id="mwAaU">Putting it in simpler words, read committed is an isolation level that guarantees that any data read is committed at the moment it is read. It simply restricts the reader from seeing any intermediate, uncommitted, 'dirty' read. It makes no promise whatsoever that if the transaction re-issues the read, it will find the same data; data is free to change after it is read.</p>
